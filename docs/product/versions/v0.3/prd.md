# v0.3 PRD：多人协作与持续工作

日期：2026-10-20。状态：planned。依赖 v0.2 已验收能力。需求共 8 项，均为 must；对应 [P03 验收](acceptance.md)。

## 1. 用户结果与范围

用户把具备不同能力的长期人物组织到群里，他们根据需求讨论、接受工作、拒绝不合适的工作、求助同事、并行执行并交付可追踪成果。工作需要等待回复时可以暂时让出运行资源，重启后仍能恢复。

平台只管理通用请求/承诺、依赖、运行与成果。资料检索、统计、写作、开发等业务验收规则由相应能力服务负责。群里不强制存在永远有最高权限的主管。

## 2. 主流程与状态

用户在群里提出目标 → 成员讨论/询问 → 一人或多人明确接受各自范围 → 各自配置/复用本次能力与资料 → 并行工作 → 需要时私聊求助或在群中交接 → 汇报成果 → 审阅指定版本 → 返工或接受。

工作状态区分待接受、已拒绝、排队、执行、等待信息/同事/审批、受阻、停止中、已停止、失败、待核对、已交付。成员发一条“我来做”后必须有对应承诺记录才算接单；静默或超时不等于接受。

工作详情显示请求者、执行者、范围/配置、依赖、运行、费用、成果/评审与真实变化。群内优先显示简洁消息和成果，原始工具流/私人推理不自动广播。协调人与其他人通过相同权限接口协作。

## 4. 数据、权限与异常

承诺、等待和工作变化在 IM 保存；领域 operation/成果在提供方保存。所有者观察可查看获准工作、记忆和 Session，但观察动作不触发运行、接受、收件处理或记忆写入。

协调策略可以使用模型辅助路由，最终授权、预算、去重和状态提交由后端决定。模型不确定时询问或保留受阻状态，不凭猜测替别人承担工作。

等待有明确对象和唤醒条件；恢复时重新核对人物/群状态、绑定版本和授权。已经发生但不能确认的效果转待核对，保持可见账本。成员退群后不能从旧等待/重试结果取得新边界之外的私密数据。

## 5. 非功能与发布门槛

至少三个人在同一群分工，另一群同时处理不同业务；用确定性故障注入验证循环等待、租约丢失、崩溃窗口和重复事件。代表性真实模型协作单独记录，不以模型输出措辞是否一致判定正确，核对承诺、真实调用、成果和权限。
