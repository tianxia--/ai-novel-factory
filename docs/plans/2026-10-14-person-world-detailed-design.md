# 数字成员协作系统：交互与执行详细设计

- 日期：2026-10-14；状态：设计提案，未实施后端，未完成真实 Harness 验证。
- 上位方案：[独立身份、个人视角与执行底座 V2](2026-10-14-person-world-and-harness-v2.md)。本文细化行为，不另起一套架构。
- 配套：[协作协议与工程契约](2026-10-14-person-world-runtime-contracts.md)、[实施拆分与验收](2026-10-14-person-world-delivery-backlog.md)、[Harness 调研](2026-10-14-open-source-harness-research.md)。
- 下文“默认”都是建议的首版产品决策，尚不代表用户已批准，也不是已经实现的功能。

最新已确认方向：以群聊和私聊组织独立人物，能力单独挂载；小说是后续领域能力，不是应用工作流主干。首版选用 OpenCode 服务式 Harness，独立 PoC 已通过；生产 IM 尚未接入。任务/审批等工程对象按需出现，不作为每轮群讨论的前置步骤。2026-10-15 新增第 21 节，明确按工作挂载能力和知识库。

## 1. 先确定产品边界

这是一个“与长期数字同事一起工作”的 IM 工作空间，不是让固定工序换上人物头像。人先于项目存在；一个人可以同时参与多个群，也可以只通过私聊完成一项工作。群不是执行引擎，项目不是人的所有者。

“像现实中的人”落在可验证的行为上：有独立身份与信息边界，会接受、协商或拒绝工作，有自己的上下文与资源，会向同事求助，对实际成果负责。独立人格是持续的行为配置和有出处的经历，不保证模型具有真实人类意识，不伪造已发生的经历。

首版默认决策：

| 决策 | 首版规则 | 原因 |
| --- | --- | --- |
| 首屏 | 我的消息，辅以待我回复、审批、验收 | 从真实沟通进入工作，不先展示流水线 |
| 团队组织 | 工作空间内人员名录；自愿接受邀请进入群 | 不把一个人锁死在一个项目 |
| 自主活动 | 由消息、已接受工作、到期提醒等可审计事件触发 | 不用无限后台自言自语模拟生命 |
| 联系范围 | 同工作空间、允许联系的成员；外部联系单独授权 | 自主求助和越权外发分开 |
| 观察 | 所有者观察自己管理的 AI，默认只读 | 观察权限不变成角色发言权限 |
| 群历史 | 默认从加入起可见；可显式共享获授权的旧消息或入群简报 | 没有入群不能自动全知 |
| 注意力 | 每个 AI 默认一个前台执行槽；不同人并行 | 保证连续性，先降低并发冲突 |
| 自主权 | 允许内部沟通和个人草稿；外发、删除、正式写回另行控制 | 按行动风险授权，不把一切交给协调者 |
| 人工接管 | 首版不支持冒用成员身份发言 | 后续必须独立设计写入租约与代发标记 |
| 执行底座 | 首版 OpenCode 服务式 Harness，正式适配器计划走 SDK | 不把底座选型替代 IM 产品建设 |

独立人格不意味着无约束自主权。协调者也只是有明确职责的成员，没有读取所有私聊、改写所有记忆或绕过验收的特权。

## 2. 人物的一生

### 2.1 创建与培养

创建分三步，首次不要求选择小说项目：

1. 身份：姓名、头像、专业方向、沟通习惯；可用模板，但每次创建都是新的 Actor ID。
2. 能力与授权：启用的技能、允许使用的工具、个人资料、可联系范围、预算上限。专业描述不是工具授权。
3. 工作偏好：默认交付标准、遇到不确定性如何询问、可自主接单的范围。完成后进入个人空间。

人格配置使用版本号。改姓名不改身份；换模型不清空关系；修改风格不篡改历史发言。正在执行的 Run 固定人格版本，普通变更在下一次 Run 生效；安全撤权立即阻止新的危险动作。

人物档案分开呈现“背景设定”“已发生的工作”“经过验证的能力”。能力验证关联真实任务和成果，关系备注带来源，不用随机亲密度或能力分数假装真实成长。

### 2.2 生命周期

| 状态 | 收件 | 新执行 | 已有执行与资料 |
| --- | --- | --- | --- |
| active | 正常 | 按调度策略 | 正常 |
| paused | 接收并排队 | 不启动 | 安全停止后进入暂停；不能只改头像状态 |
| archived | 不接受新任务，发信前提示不可联系 | 不启动 | 保留授权范围内历史；未完成承诺须交接或取消 |

离线是运行可用性，不是人物被删除；离群也不销毁人物。归档前列出未交付工作、待审批动作、待核对外部效果，逐项处理。恢复归档人物时先复查权限，不自动恢复过期令牌。

首版提供归档，不提供一键清空全部经历。数据删除、导出与保留期限是独立管理流程，不能靠删除 Session 假装完成所有存储的删除。

## 3. 页面、操作和空状态

### 3.1 信息架构

全局栏：工作空间、观察对象、观察状态、返回我的视角。个人导航：消息、群组、联系人、工作、资料、记忆、运行会话。设置与管理员诊断独立进入。

桌面消息页采用会话列表、消息时间线、可折叠详情；窄屏按列表、消息、详情逐层进入。视角标识始终可见。除实际重复条目和交付对象外，不把页面分区包装成多层卡片。

| 页面 | 主内容 | 我的视角可做 | AI 观察视角可做 | 空/异常状态 |
| --- | --- | --- | --- | --- |
| 消息 | 私聊、群聊、提及、投递状态 | 发消息、引用、共享获授权资料 | 阅读、追溯来源、以我身份联系 | 无会话显示联系人入口；断线保留草稿 |
| 群组 | 当前群、邀请、已归档群 | 建群、接受邀请、按权限管理 | 查看其群和加入边界 | 邀请未接受不显示讨论预览 |
| 联系人 | 已联系的人、团队名录、合作记录 | 私聊、邀请、屏蔽 | 查看其关系和约定 | 新成员仍可有允许联系的团队名录 |
| 工作 | 接下的、发出的、待我决定、历史 | 请求、协商、审批、验收 | 阅读该成员工作的因果链 | 没有工作时不造示例进度 |
| 资料 | 个人草稿、获授权资料、成果版本 | 上传、共享、撤销授权 | 阅读其有权使用的内容 | 撤权显示不可用，不返回原文摘要 |
| 记忆 | 人格版本、经验、约定、来源 | 管理自己授权的资料；管理 AI 另走设置 | 查看可观察内容与来源 | 没有经验时明确为空 |
| 运行会话 | 用途、状态、输入、工具、用量 | 查看授权范围；管理动作另入口 | 只读检查当前人物 | 损坏时只显示诊断，不触发自动恢复 |

“以我身份联系陈墨”必须先切回人类身份，打开我与陈墨的私聊，不在陈墨与林岚的聊天底部插入我的发言。

### 3.2 建群和启动项目

1. 选择联系人、群名；可选项目，不要求先选流程模板。
2. 发出邀请，未接受者在成员列表显示“待加入”；AI 可以根据权限与现有负荷接受或说明冲突。
3. 群创建者发布目标。首版可选“指定协调人”，但这个职责也需要对方接受。
4. 协调人或任何成员提出分工。每项工作分别确认负责人、交付物、验收者和截止时间；尚未确定的字段可协商。
5. 接受后出现在各自工作台。群内显示简洁的承诺记录，详细步骤留在个人工作区。

不强迫每个群采用项目管理。临时讨论群没有项目、任务或负责人也是有效群。

### 3.3 表达分歧与变更

成员可以提出反对意见和替代方案，不必模拟永远一致的团队。普通意见直接发言；会改变已经承诺的范围、期限、正式设定或预算时，形成带版本的变更建议。

变更卡显示原约定、建议差异、影响的交付物、需要确认的人。协调人汇总不代表有权批准。授权的决定者确认后才更新正式版本，并向受影响的人投递事件。

## 4. 视角隔离不是前端过滤

请求必须区分三个身份：

- `principalId`：谁登录并实际操作，例如真实用户。
- `perspectiveActorId`：当前观察谁，用于经授权的数据投影。
- `actingActorId`：谁在执行动作，由登录身份或可信运行令牌推导，不能由页面任意传入。

观察接口只返回当前人有权观察的对象。管理员查询和 Agent 工具检索使用不同授权入口；不能把管理员全量响应交给模型后让它自行忽略。

建议前端缓存键为 `principal + workspace + perspective + mode + grantEpoch`，Session 缓存还包含 logicalSessionId 和 epoch。切换时取消旧读取和订阅，递增请求代次，迟到响应必须丢弃。保留原视角草稿及定位，但不把它们渲染到新视角。

查看成员不改变 delivery、processed、工作状态或模型调用数。观察审计与成员业务状态分离。权限撤销后使敏感缓存失效，重新授权前不展示上一份响应；客户端清除不能被描述为能够收回已经复制出去的信息。

## 5. 消息的真实语义

### 5.1 一份聊天事实，多份个人处理状态

消息不可变，使用 `conversationId + seq` 确定顺序；同一 DM 的双方看到同一个 messageId。联系人备注、置顶、草稿和收件状态各自保存。

| 内部状态 | 含义 | 不能推出 |
| --- | --- | --- |
| persisted | 消息已提交到业务库 | 对方已在线 |
| delivered | 已进入该接收者的持久收件箱 | 模型已收到 |
| admitted | 已确认纳入某次执行的输入 | 对方理解或同意 |
| handled | 执行记录已作处理决定，可包含不回复 | 已完成这项工作 |
| replied | 存在明确关联的回复消息 | 已接受工作或验收成果 |

人类手动已读和 AI 处理记录不是同一个字段。观察者阅读不推进任何接收者状态。一个 Run 崩溃时保留 admitted，不能伪装 handled。

按消息保存处理结果；“已处理到 seq=N”只允许表示连续无洞的范围，不能因先处理一条高优先级新消息就跳过更早的待处理项。

### 5.2 消息命令草案

下面是本项目拟议接口，不是任何 Harness 的原生 API。

```json
{
  "clientRequestId": "req-example-01",
  "expectedMembershipVersion": 3,
  "text": "请确认首章人物动机。",
  "mentionActorIds": ["actor-lin"],
  "replyToMessageId": null,
  "attachmentVersionIds": []
}
```

`POST /api/collab/conversations/:id/messages` 从可信上下文确定发件人。相同幂等键和相同正文返回同一结果，不同正文返回冲突。正文中的名字不是授权的 @；引用与附件也要独立做可见性检查。

客户端发送失败保留草稿与请求 ID。重新发送复用请求 ID，只有“作为新消息发送”才生成新 ID。不把 HTTP 超时当作服务端肯定没收到。

撤回保留 tombstone 和审计。接收者若已经纳入工作上下文，后续必须投递撤回/更正事件，不承诺让模型忘记；已经引发的工具效果单独核对和补偿。

### 5.3 谁应该说话

群消息投递和模型唤醒分开。所有具备消息可见权的当前成员收件，调度只唤醒有理由行动的人：直接被 @、收到明确请求、被回复、负责的依赖变化，或承担本轮讨论职责。

普通未定向消息默认先由已接受职责的协调人处理；无协调人时群可选择“定向回复”或“开放讨论”。开放讨论每轮按专长与负荷挑选有限成员，允许不发言；选择不授予其额外资料权限。

每次自主讨论绑定 causeId、轮次、调用预算与截止条件。建议试点最多三轮内部追问后汇总阻塞并交给请求者决定；这是可调护栏，不是模型能力结论。礼貌确认不触发新一轮全员答复，重复的无进展循环被暂停。

## 6. 从请求到真正交付

聊天是自然语言入口，但关键工作事实必须由结构化命令确认，不能用字符串匹配“好的”直接标记接单。

### 6.1 三个不同对象

| 对象 | 解决的问题 | 主要字段 |
| --- | --- | --- |
| Request / Commitment | 双方到底答应了什么 | requester、assignee、termsVersion、范围、交付物、验收者、期限 |
| Task | 接受后工作的进展 | commitmentId、owner、dependencies、status、acceptedArtifactVersion |
| Run / Attempt | 这一次实际执行了什么 | actor、session、inputIds、toolCalls、result、usage、attempt |

一个 Task 可以经历许多 Run；一次模型失败不等于成员拒绝工作；一次工具成功不等于请求者验收。

### 6.2 承诺状态

`proposed -> accepted | declined | withdrawn | expired`。

需要澄清时追加问题，仍保持 proposed。accepted 时用事务创建 Task，保证重复点击只建一个。已接受的承诺不能靠修改原 JSON 改期限；新条款先成为 proposed revision，对方确认前旧条款仍有效。撤销已接受工作进入 Task 的取消流程，不回写成“从未接受”。

### 6.3 工作状态

| 状态 | 进入条件 | 允许下一步 |
| --- | --- | --- |
| ready | 承诺已接受，依赖满足 | running、cancel_requested |
| running | 获得成员租约并开始执行 | waiting、submitted、failed、cancel_requested |
| waiting | 等待回复、资料、审批或依赖，理由和期限明确 | ready、failed、cancel_requested |
| submitted | 交付不可变成果版本 | changes_requested、accepted_pending_apply、cancel_requested |
| changes_requested | 审阅人提交针对版本的修改意见 | ready、cancel_requested |
| accepted_pending_apply | 验收确认且记录具体版本 | completed、apply_blocked |
| apply_blocked | 领域门禁或正式写回失败/未知 | 经核对重试到 accepted_pending_apply，或提出修订 |
| completed | 验收与要求的领域写回均确认成功 | 终态；新需求建新工作 |
| cancel_requested | 已有执行需要停止并核对效果 | cancelled、reconciliation_required |
| cancelled / failed | 安全结束或明确失败 | 显式重开为新尝试并保留历史 |
| reconciliation_required | 外部效果不确定 | 人工或查询确认后到取消/失败/已确认结果 |

普通任务没有领域写回时，验收可同事务完成。小说任务不能在 Canon 写回失败时提前显示“完成”。`submitted` 不能被新草稿覆盖，审阅与验收必须携带 artifactVersionId 和 expectedTaskVersion，旧版本操作返回冲突。

转交工作要让新负责人接受。原负责人在交接完成前仍负责说明现状；转交不是修改 assigneeId 就丢失来源和未确认副作用。

### 6.4 人类与 AI 的确认方式

人类点击接受、拒绝、提交修改意见、验收。AI 通过相同业务命令执行，响应中返回持久化回执，公开消息引用这些回执。模型只生成“我接受”但工具未提交时，UI 不显示已接受。

AI 可在预授权的范围内自行接单；超出预算、工具权限或承诺能力时须协商。验收人可以是另一个 AI，但正式发布、删除等高影响动作按独立规则审批，不能用成员互相同意绕开。

## 7. 求助、等待与恢复

以“陈墨写首章，向林岚问动机”为例：

1. 陈墨调用业务命令 `askAndWait`，携带目标人、问题、关联任务和截止条件。
2. 同一业务事务创建 questionId、消息、等待条件和 outbox，避免消息发出后还没登记等待就收到回复。
3. 当前执行到安全点后收束；确认 Harness 已静止才释放注意力租约。任务标记等待，不让 worker 阻塞等同事。
4. 林岚在自己的 Session 中收到问题，读取自己有权使用的信息并回复，引用 questionId。
5. 明确的答案通过 `answerQuestion` 命令引用 questionId，提交事务匹配等待条件，写入唯一的唤醒事件。普通“收到，稍后回复”只作为消息投递，不满足问题等待条件。即使答案先于运行结束到达，事件也会留在队列，待租约释放后处理。
6. 陈墨恢复原任务逻辑 Session，加入这份已授权回复，继续工作。不是新造一个没有历史的陈墨。

`waitId + matchedEventId` 唯一，重复回复通知不产生重复执行。任务取消会关闭等待条件，晚来的消息仍是真实收到的消息，但不复活已取消工作。

到期未回复时按事先设置的次数提醒或向请求者报告阻塞，不假造对方回答。A 等 B、B 又等 A 时检测依赖环；提示缩小问题、提供部分结果或请求人类裁决，而不是永久占用线程。

## 8. 人格、记忆与 Session 如何配合

人物长期身份不等于一个无限增长的大 Session。建议至少区分：

| 上下文 | 所属者与用途 | 生命周期 |
| --- | --- | --- |
| 个人收件处理 | 本人分拣请求和维护承诺 | 懒创建，可分段；不能任意发到公开群 |
| 私聊上下文 | 本人在一段 DM 中的工作历史 | 双方各自一份，公开聊天事实共享 |
| 群聊上下文 | 本人在群内的公开沟通历史 | 每人独立；只包含其可见消息 |
| 任务上下文 | 本人处理某项工作 | 可跨多次 Run，归档后留可恢复检查点 |

陈墨和林岚私聊意味着一份聊天历史和两份私人 Session，不是让同一个 Session 轮流改名演两个人。切换 Harness 可以重建逻辑上下文，但不承诺原生推理历史无损迁移。

输入组装顺序建议：固定人格版本、已授权能力、当前任务与承诺、可使用的来源、待处理消息。每个来源包含 origin、owner、audience、purpose 和版本。对方的话是有作者标识的外部输入，不伪装成本人的 assistant 消息或系统指令。

跨项目经验要抽取可复用方法，不能顺带把客户原文带到另一个群。经验写入有出处、置信状态和修订记录；成员对关系的主观备注不升级为对方已经承诺的事实。

### 8.1 知道和允许说不同

来源访问权与披露权分开检查。执行公开群回复时，只装入允许用于该群和该目的的资料；敏感个人资料不能先进入群回复 Session 再靠提示词要求闭嘴。

受限的私人任务 Session 需要发布成果时，默认提交草稿与来源清单，经披露检查或授权后再发布。无法可靠确定披露范围时转待审，不把任意自由文本过滤器宣传为形式化的数据防泄漏保证。

### 8.2 撤权必须处理旧上下文

禁止继续检索不足以撤销已有上下文：

1. 递增授权版本，工具网关立刻拒绝旧授权的新调用。
2. 根据输入来源索引找到受影响的活动 Session，停止或隔离它们。
3. 从仍被授权的历史和资料重建新 epoch；包含已撤销来源的摘要不能作为重建输入。
4. 旧原生日志转受控隔离状态，观察接口重新授权；不允许 Agent 自动 resume 旧实例。

系统能阻止未来读取和继续使用，不能承诺撤回已经发给别人、复制到外部或提交给模型供应商的数据。来源依赖不完整的 Session 采用保守隔离，而非假定没有污染。

## 9. 调度与停止

默认每个成员一个 attention lease，包含 owner、expiresAt、fencingToken。续租失效后，业务写入拒绝旧 token；外部非幂等动作另用效果账本，租约本身不能撤销已经发生的网络请求。

优先级建议：停止与撤权控制 > 正等待的审批/答案 > 有期限的已接受工作 > 定向新请求 > 非定向讨论。使用等待时间提升优先级避免饿死，不用新消息无条件打断正在提交的成果。

等待同事释放工作执行槽；等待 Harness 原生工具审批是否可以释放，取决于底座是否支持安全挂起。不能为了显得并行就让同一个 Session 有两个写者。不同 Session 的任务切换也须保持成员承诺与工作所有权一致。

停止按钮先变为“停止中”。确认底座执行及其子工具收束后才显示“已停止”；外部状态不明显示“待核对”。不可停止单个成员而只能杀死所有人的部署方式不能通过默认底座准入。

## 10. 数据约束与事务

沿用 V2 表设计，第一期只建其闭环必需表，不提前实现完整企业组织或无限关系图。所有业务事实仍以 `.ai-novel-factory/factory.sqlite` 为权威。

必须在数据库或同等强度的事务边界保证：

1. 关联对象同 workspace；使用复合外键或受测事务校验，不能只依赖 UI 参数。
2. DM 对参与者 ID 排序规范化，`workspace + lowerActor + higherActor` 唯一。
3. 群成员关系分 membership epoch；重新加入不能误恢复已撤销历史权限。
4. `conversation + seq`、`actor + inboxEvent`、接受承诺生成的 Task 各自唯一。
5. 每个逻辑 Session epoch 只有一个活动 Harness binding；每个成员只有一个有效前台租约。
6. 发送消息、收件投递、业务事件、outbox 同事务提交。
7. 接受工作、提交/验收成果、取消均使用 expectedVersion 做乐观并发控制。
8. 工具效果持久化 effectId、参数摘要、作用对象、授权与核对状态；不是只有日志文本。

消息和领域状态保留可追溯事件，但不要求把整个系统改造成全量 event-sourcing 框架。当前快照与必要审计已足够支撑首版。

### 10.1 跨库故障

Harness 日志与业务库不能假装共同事务。输入投递记录状态为 prepared、submitted、acknowledged 或 uncertain；不确定时先查询外部输入/Session 记录，无法确认则停在待核对，不盲目再发。

业务工具由服务端签发效果许可，绑定 run、逻辑操作、资源版本和参数。相同 effectId 重试返回原回执；模型重试产生新的 toolCallId 时必须关联已有操作意图，不能把新 toolCallId 当作“肯定是新动作”。

对无法提供幂等键或结果查询的外部服务，不能承诺通用 exactly-once。高风险效果优先经受控连接器执行，网络超时后的 unknown 必须核对；无核对路径时人工决定，不自动重复购买、发送或发布。

### 10.2 订阅与权限

业务 SSE 使用本系统事件序号及可验证的恢复游标。订阅服务器同时检查 principal、perspective 和当前授权。重连先做授权和快照校验，不能用旧游标恢复已撤权内容；事件过滤发生在服务器，不能将全局事件广播后再由前端隐藏。

## 11. API 行为契约

| 命令/查询 | 关键检查 | 返回与副作用 |
| --- | --- | --- |
| `GET /perspectives` | 当前人可观察范围 | 不返回无权成员的名字或计数 |
| `GET /actors/:id/conversations` | 观察权 + 该成员的会话可见权 | 只读，不发已读回执 |
| `POST /conversations/direct` | 当前执行者联系权、同空间 | 同一对人幂等返回同一 DM |
| `POST /conversations/:id/messages` | 成员版本、附件/引用、发送人 | 消息+投递+outbox 原子提交 |
| `POST /requests/:id/accept` | 指定接收者、条款版本 | 承诺+Task 原子提交 |
| `POST /tasks/:id/ask-and-wait` | 负责人、联系权、任务版本 | 问题+等待条件+消息原子提交 |
| `POST /tasks/:id/deliveries` | 负责人、成果不可变版本 | 进入 submitted，不直接完成 |
| `POST /tasks/:id/reviews` | 验收/审阅权限、目标版本 | 修改意见或验收；调用领域门禁 |
| `POST /runs/:id/cancel` | 实际操作者管理权 | 返回取消请求，不伪造即时停止 |
| `GET /sessions/:id/inspection` | 观察权、来源权限、脱敏 | 不 resume、不修复、不触发模型 |

以上路径以 `/api/collab` 为前缀。所有写命令带 clientRequestId，涉及竞争的命令带 expectedVersion。建议错误码：`version_conflict`、`membership_changed`、`budget_exhausted`、`effect_uncertain`、`session_rebuild_required`。

无权对象对不应知道其存在的请求者返回统一 not_found；已知对象因自身成员变动失效时，可返回不含其他人敏感信息的 membership_changed。

## 12. Harness 适配契约与验证

首版采用 OpenCode。进程管理启动 headless 服务，正式 worker 计划通过版本匹配的 SDK 调用，不解析 CLI 对话；SDK 是服务客户端。当前独立 PoC 直接使用 HTTP，验证了 Session、两组本地 Provider 配置、工具、停止和正常重启；SDK 类型、SSE 和生产恢复仍待验收。本机 1.14.33 的 `/doc` 未列出完整 Session 路径，不能只依赖它生成客户端。[验证报告](2026-10-15-opencode-im-poc.md)、[官方 SDK](https://opencode.ai/docs/sdk/)

审批配置不是我们的业务授权。即使 Harness 允许工具执行，也必须通过本项目工具网关校验身份、资料范围和效果许可；不启用全局自动批准来绕过产品审批。[官方 Permissions 文档](https://opencode.ai/docs/permissions/)

以下是拟议的能力契约，不是声称这些底座都存在同名方法：

| 契约 | 必需语义 | 不支持时 |
| --- | --- | --- |
| capabilities | 声明持久化、单运行停止、steer、审批、恢复等能力 | 不虚构统一能力 |
| create / resume | 绑定 actor、logicalSession、epoch、工具授权 | 明确拒绝恢复不兼容历史 |
| submit | 有 invocationId 和接收回执 | 超时进入 uncertain，先查询 |
| inspect | 只读取得已提交日志与状态 | 不能通过 resume 代替观察 |
| events | 映射输入、工具、审批、用量和状态 | 不把文本结束当作执行完全收束 |
| cancel / settle | 指定执行停止，确认无后续危险动作 | 独立进程隔离或拒绝准入 |
| approve | 审批绑定具体参数、资源版本与期限 | 不降级为一律放行 |
| checkpoint / close | 给出恢复资料和原生格式版本 | 明确迁移损失，重建 epoch |

工具环境隔离、受控网络和凭据代理由部署方案保证，不能只为每个人设置不同 cwd。Harness 服务不直接暴露给 UI 或成员；SDK/REST 原生接口只由受信适配器访问。

测试固定模型/工具/输入，并记录版本、依赖锁、用量和原始回执。覆盖三个独立成员、双向私聊、等待恢复、单人取消、崩溃恢复、只读观察与隔离。本轮未运行这些用例，不能把用户在其他项目的 Pi 试验扩大为本项目验收通过。

## 13. 与现有项目的集成位置

建议先保持当前包边界，避免为未稳定接口拆出大量新包：

- `packages/ai-novel-core`：新增 collab 业务模块、授权、收件调度、Harness 适配接口、效果账本。复用已有 DB 和 worker 基础设施，不复制第二套项目状态。

## 14. 分阶段范围与迁移

第一条纵向闭环只验证“一个人提出工作，两位成员私聊协作，交付可验收成果，我能观察双方但不改变他们的状态”。先用确定性测试适配器跑通，再接一种真实 Harness。

首版暂不实现：跨组织人物市场、真实用户之间的管理者全量窥视、复杂企业层级、人工冒用成员、无限后台心智循环、多 Harness 无损热迁移、模拟生理生活。

权限隔离、可恢复投递和幂等从第一条闭环开始，不拖到 UI 做完以后补。资料记忆 UI 可后置，资料授权与输入来源约束不能后置。

旧小说迁移顺序：建立一致备份检查点，停旧调度并确认工具收束，保留原作者历史，创建经用户确认的人物映射，切换项目执行所有者，完成一章验收后再扩大范围。不能让旧 autopilot 和新群协作同时推进同一小说。

回退关闭新入口并停止新执行，保留新成员、消息和效果账本。已经发生的新沟通不能通过直接恢复旧 DB 快照抹去；需要兼容读取或专项恢复方案。

## 15. 交互样例与证据边界

配套交互样例展示“我 / 陈墨 / 林岚 / 周宁”的不同会话、工作、资料、记忆和 Session，以及只读观察和返回本人沟通。陈墨与林岚共享一段 DM，但周宁和我的正常会话列表没有它。

样例数据完全虚构，仅供确认信息架构与交互，不调用模型，不连接生产数据库。客户端隐藏只能用于表现行为，不能作为后端权限隔离的证据。后端验收必须使用直接 API 请求、故障注入和真实底座执行。

## 16. 人格如何保持连续，而不只是提示词

### 16.1 一个人物的六个组成部分

| 部分 | 保存什么 | 谁可以改变 | 不代表什么 |
| --- | --- | --- | --- |
| 稳定身份 | Actor ID、显示资料、创建来源、所属工作空间 | 所有者管理，身份 ID 不变 | 不等同某个模型名或进程 ID |
| 人格版本 | 工作价值偏好、表达方式、遇到不确定性时的习惯 | 管理者确认新版本；成员可提出建议 | 不产生额外授权，也不证明真实意识 |
| 能力配置 | 声明专长、启用的技能版本、工具能力和限制 | 所有者授予；成员不能自行扩权 | 声明擅长不等于通过实测 |
| 经历 | 已接受/完成工作、交付物、评价、协作事件 | 从持久业务事实生成，纠错保留来源 | 不是模型编写的虚构履历 |
| 关系 | 与特定人的约定、沟通偏好、联系政策 | 本人的有来源备注或双方真实确认 | 单方印象不是对方的承诺 |
| 当前状态 | 注意力、计划、承诺、Session、可用资源 | 由工作事件与授权操作更新 | 换群不创建一份互不知情的新身份 |

运行时读取这六部分的必要且被授权的子集，不把所有人生记录塞入每次 prompt。人格只是其中相对稳定的一层；实际能力与工作结果由工具、模型和证据共同决定。

### 16.2 人格字段要能观察到行为

初版不设计抽象人格分数，优先使用有明确作用的配置：

- 表达方式：简洁直接、温和解释、先给结论等；可以组合，不强迫所有回答使用固定口头禅。
- 工作偏好：先核对资料、先给草稿、倾向提出备选方案等。
- 不确定性处理：缺关键事实时询问，区分事实与假设；不能靠自信语气代替证据。
- 分歧处理：先说明依据，保留不同意见，重要约束交给有权决定的人。
- 专业关注点：例如人物动机、事实一致性、交付结构；不是硬编码执行顺序。

人物差异必须允许在同一个问题上产生不同关注点和建议，但不能以“性格强势”为由越权，以“创意丰富”为由伪造事实。安全和授权规则不进入可随意调整的人格滑块。

### 16.3 经历、经验与长期规则

经历由真实事件形成。任务完成后，成员可在已批准的预算内提出一条经验候选，例如“交付正文时附所用章纲版本”，包含来源、适用范围、反例和是否需要复核。

首版采用轻量流程：`candidate -> confirmed | rejected`，已确认经验可进入 `superseded / revoked`。系统可以自动保存任务经历；模型生成的概括不能自动升级为永久通用规则。初期由所有者确认可复用经验，不为每条普通聊天都创建记忆审批。

明确的项目约定可以直接从已确认业务命令派生，并保持项目范围；跨项目通用经验需要单独确认和披露检查。对同一个来源反复总结不算多次独立证据，也不能通过复制摘要提高可信度。

使用经验前检查：来源是否仍有效、当前用途是否匹配、是否被新版替代、是否有权使用和披露。来源撤销不仅隐藏来源链接，还应使依赖它的经验、摘要及索引失效，按既定规则重建受影响 Session。

### 16.4 能力成长的证据

能力页面分三列语义，不用一条经验值混在一起：

| 语义 | 示例 | 更新规则 |
| --- | --- | --- |
| 声明专长 | 人物塑造、长文编辑 | 来自档案配置，不展示为认证结果 |
| 可用能力 | 资料阅读、个人草稿、受限检索 | 来自有效工具/资源授权和已安装版本 |
| 已验证成果 | 某任务的具体版本通过谁的验收 | 关联真实成果；一个任务成功不等于全面能力认证 |

学习一份手册可以新增知识来源或经验候选，不能直接获得 shell、网络或发布权限。新增可执行技能/扩展需要所有者确认来源、版本、权限和隔离测试；检索到的文档不能自动成为可执行插件。

“这个人物更擅长了”应通过同一组代表性任务的表现、实际返工与用户评价来说明。首版不自建模型训练系统，也不承诺保存记忆必然提高模型能力。

### 16.5 人格和模型升级

换模型、更新人格、更新技能是三个版本事件。每次 Run 记录各自版本，升级不改写历史。更换前做小范围回归，检查人物身份、已有承诺、信息边界和任务能力；普通升级默认在当前执行收束后生效。

对照用例包括：被要求冒充另一成员、被要求忘记已接受任务、被要求转发私有资料、在多个群间切换、压缩后继续工作、来源更正后更新判断。事实与权限要求用确定性断言，沟通风格和专业质量由人工抽查，不只靠另一个模型打分。

回退人格版本不会删除这段时间真实发生的经历和外部效果。无法与旧原生日志兼容时新建 Session epoch，说明重建来源，不宣称把人物时间倒回去了。

## 17. 四条完整用户操作流

### 17.1 创建成员并开始认识他

| 步骤 | 用户操作与页面 | 系统行为 | 异常处理 |
| --- | --- | --- | --- |
| 1 | 团队名录点击新增成员 | 打开三步配置，创建前不写正式 Actor | 取消保留本地草稿，可明确丢弃 |
| 2 | 填姓名、专长、工作偏好 | 预览档案；同名允许但显示身份标识 | 必填为空原位提示；不将人设当作真实履历 |
| 3 | 选择资料、工具、内部沟通范围和运行配置 | 展示实际权限与限制 | 没有可用模型/底座可先保存为暂停，不阻塞建档 |
| 4 | 确认摘要并创建 | 单事务建立 Actor、人格 v1、个人空间与授权引用，返回稳定 ID | 重试同请求不重复创建；部分失败回滚，不留半个人物 |
| 5 | 打开新人物档案 | 经历、已验证成果、记忆初始为空 | 不自动生成假欢迎履历或假朋友圈 |
| 6 | 进入我与他的私聊 | 以我的身份建立/返回同一 DM | 暂停成员可收件但不执行，明确显示等待启用 |
| 7 | 管理者启用 | 检查底座可用性、授权、隔离和预算，再接收工作 | 检查失败仍暂停；网络连通不等于安全/能力验证通过 |

创建和启用是两个动作。首版默认先创建为 paused，配置检查后由所有者明确启用。成员可以没有小说项目，也不会自动出现在任何群里。

### 17.2 私聊交办，不要求先建群

用户可以直接发“帮我整理一份读书会邀请函”。聊天与任务不是两个互不相通的系统，但也不能把所有问句自动当成后台任务。

明确任务可以通过输入区的交办入口提交最少字段，或由成员从消息识别工作请求。交办策略提供两种模式：授权范围内直接接单，或先展示建议由用户确认。本轮建议前者，更贴近同事协作；此偏好已询问用户，尚未收到选择，不能视为已确认的产品决定。

直接接单仅限来自已认证请求者的明确任务，并受现有资料、工具、预算和任务类型预授权约束；不确定或超出范围先澄清/审批。接收者提交业务接受命令时，服务端从不可变源消息派生请求来源与实际作者，记录“基于消息和预授权接受”，不能伪造用户点击过确认。引用他人发言不等于那个他人实际授权。

条款区分原消息明确内容、版本化默认约定和成员提议。成员回显自己的理解；模型理解可能出错，所以不能静默补硬截止时间、扩大预算或授予新能力。需要更严格控制时使用确认模式，或单项要求用户确认。内部同事协作仍按各自权限和预算独立处理。

普通简短答疑直接回复，不强迫创建任务卡。范围、交付物、时限、预算不清时保留为沟通；成员不能替用户补一个硬截止时间或批准新的消费。

| 节点 | 用户可见内容 | 关键约束 |
| --- | --- | --- |
| 工作识别/建议 | 实际来源、目标、交付形式、条款来源、未确定项 | 不能把猜测或转述伪装成用户确认 |
| 授权或确认 | 已有预授权范围；需确认时一次提交条款 | 请求来源由服务端核验，不由模型任意填写 |
| 成员接单 | 接受/协商/拒绝记录 | 用户不用替 AI 点击接受；AI 走业务命令 |
| 工作进行 | 当前状态、交付约定、必要阻塞 | 不用假打字表示真实执行；不泄露同事私聊 |
| 交付与修改 | 明确版本、依据、修改意见 | 修改产生新版本；先前反馈保留 |
| 完成 | 验收与要求的正式应用均成功 | 不强制把私人任务公开到群 |

“确认交办”只确认任务条款，不等于批准任务可能涉及的所有工具。外部发送、删除、发布等效果仍按具体许可执行。

### 17.3 从私聊扩展为项目群

用户发现工作需要多人时，从私聊选择创建项目群，选择成员、可选项目与准备共享的资料。新群使用新 Conversation ID，原 DM 保留。

入群简报是一份新共享内容，默认由用户选择或确认，列出目标、已确认约定、待决问题和获准共享的成果；不自动复制整段私聊、私人笔记或 Session。邀请尚未接受的成员不能看到群讨论正文。

已有私人任务是否关联新项目、是否向群共享进度/成果、是否改变负责人，分别确认。仅关联项目不会扩大任务可见范围；转交负责人还需接替者接受。协调人收到的也是获授权简报，不是全知历史。

成员自行求助可继续使用双方 DM。对群有影响的决定再形成公开建议；不把“私聊搬到群”作为协作的必经路径。

### 17.4 交付、反馈与下一次合作

成果提交后在消息中出现版本条目。打开详情可以阅读正文、查看所用依据、查看审阅意见、比较授权范围内的版本；作者和观察者不能因为看得到页面就自动获得验收操作。

验收人可以接受此版本或提出具体修改。作者提交新版本后，旧版本页面仍可读，但不能对已经失效的任务版本提交新审批；客户端与服务端都要处理冲突。

完成时同时生成成果记录和真实工作经历；自动产生经验候选是可选后台任务，需要预算，不能延迟已完成任务的显示，也不能无限复盘。候选被确认后，下一项适用工作才会检索到它。

下次用户联系同一个成员时，人物可以延续获授权的合作约定。对于没有来源或已被撤销的细节，不能为了显得熟悉而编造“上次你说过”。

## 18. 首版范围与界面渐进展开

首版包含一个真实所有者、多个自有 AI、对等私聊、群邀请、只读视角、个人任务、版本交付、来源明确的资料/经验，以及一种真实 Harness。人数和并发上限由 PoC 测量后确定，不把样例的三个人写成产品上限。

初次使用首先提供消息和团队名录；人物被创建后才有其个人空间。资料、记忆和运行会话可以作为个人空间里的次级入口，不要求首屏塞满七列功能。高级运行配置、权限和诊断放管理入口；普通交办不暴露原生 Session ID 和租约字段。

| 首版必须有 | 首版暂缓 |
| --- | --- |
| 创建/暂停/归档人物，版本化人格与明确工具授权 | 人物市场、跨组织导入真实用户身份 |
| 任意允许的双方私聊，邀请入群，成员视角 | 大型组织层级、公共社交动态、模拟生活需求 |
| 接单/协商/拒绝，等待求助，指定版本验收 | 多数投票引擎、复杂企业审批流 |
| 私有资料与披露边界，有来源的经历/经验 | 无限制自主学习、自动安装外部技能、自建模型训练 |
| 一种默认 Harness，单人停止、恢复和只读检视 | 多底座无损热切换、人工冒用 AI 发言 |
| 旧小说能力适配、正式门禁与增量迁移 | 为新概念同时重写前端框架和全套领域引擎 |

能力验证展示证据，不以“人格一致率”单个数字宣称真实独立人格。人格被注入、信息泄漏、重复副作用和丢失承诺是发布阻断；风格差异和主观质量要另做产品评估，不能平均抵消安全失败。

## 19. 本轮创建成员交互样例

新增局部样例展示档案、能力授权、创建确认、暂停后的个人档案及本人私聊入口。它只在样例内保存状态，不启用真实人物、模型或工具，也不安装技能。实际操作流与权限须通过实施清单验证。

样例与正式产品的差异：运行配置仅表示未绑定状态，创建结果固定暂停，私聊发送只作本地交互展示，不生成 AI 回复、不执行真实任务。

样例已检查必填字段、预算范围、跨步骤校验、权限摘要、暂停建档、空经历/记忆、同一人物的配置版本变更、取消编辑、长姓名、私聊草稿保留和正文转义。完成 736/360/320px 与深浅主题检查，未出现浏览器脚本错误。配置版本是样例内记录，不代表真实人格、授权或 Harness 版本已接入；上述检查不替代后端与真实底座验收。

## 20. IM、人物模型与独立能力配置

### 20.1 普通用户从群聊开始

已有成员时，主流程是新建群、邀请编剧/作者/编辑、提出创作要求、群内讨论、各自开展工作、带着问题或成果回到群里。成员可以先讨论而不立即分工，可以并行工作，也可以只通过私聊协助。不要在创建群之前要求创建小说工程、选择生产阶段或填写全部任务条款。

普通交流使用人物的会话 Session；需要连续执行工具工作时，才按需要创建关联的工作记录和任务 Session。并非每轮对话都先走 Request/Commitment/Task。成员的长期身份和个人记录提供连续性，群公开历史与个人运行上下文分别保存。

### 20.2 三个独立设置入口

| 入口 | 用户配置 | 不放在这里 |
| --- | --- | --- |
| 工作空间设置 / 模型服务 | Provider 实例、协议与端点、凭据引用、模型目录、可用状态 | 人物性格、小说阶段、群分工 |
| 人物详情 / 模型 | 该人物的 Provider 与模型、实际支持的推理/输出选项 | 直接展示原始 API Key，修改其他人的默认模型 |
| 能力库与人物详情 / 能力 | 能力定义、技能版本、工具授权、允许的资料与操作范围 | 模型供应商即工具权限、角色名即自动授权 |

人物创建时可继承工作空间默认模型，也可另选；保存的是明确的模型绑定，不因其他人物选了不同模型而一起变化。不同人物可以使用不同 Provider，也可共用一个获准 Provider 实例而拥有不同模型、Session 和能力授权。

Provider 中的敏感凭据留在受信配置/凭据存储，普通人物和群消息只获得必要的模型标识与调用能力。底层支持某协议不表示所有接入端点都支持相同工具调用、多模态或推理选项；只展示实际版本与模型配置允许的能力。

### 20.3 配置与生效

1. 所有者添加 Provider，填写必要连接配置；服务端验证配置，显示脱敏错误。需要收费的连通测试应明确提示。
2. 读取可用模型目录；若实际适配器支持手动模型配置，则允许显式添加，不虚构端点返回的能力。
3. 给人物选择模型，独立选择能力包与允许范围；没有可用模型时可保存人物，明确显示不可执行。
4. 调度人物时固定本次模型绑定、人格版本、能力版本与授权快照，创建或恢复所选底座的对应 Session；不会因为在同一个群就共享一个模型 Session。
5. 更新模型默认在当前 Run 收束后生效。身份、消息与经历保持不变；原生上下文不兼容时明确重建，不承诺无损热切换。
6. Provider 失效时保留收件和工作，显示模型不可用。只有用户已允许的备用模型可切换，记录实际使用者；不静默把私有资料发送到另一家服务商。

### 20.4 小说能力挂载示例

以下是拟议业务能力名，不是声称现有工具已经实现：编剧可配置故事设计、人物设定与章纲工具；作者可配置读取已共享设定、章节写作与修改工具；编辑可配置审稿与一致性检查工具。正式设定修改和发布权限独立授予，不由“作者”或“编辑”称号自动推导。

同一能力可以授权给多人，每次调用仍带实际人物、来源会话、资料范围和执行回执。先做普通 IM 与人物能力挂载，后接小说能力；不把旧完整流水线挂到一个人物身上后，再将其内部阶段冒充成多人协作。

## 21. 按工作挂载能力与知识库

### 21.1 人物不变，工作配置可变

同一个人物可以参与不同工作，使用不同能力、知识库和工具账号。人格、身份、专业经验保持连续；本次工作的资源配置独立版本化。不是每换工具就创建一个新人物，也不是把全部工具和所有知识永久塞进一个 Session。

| 层级 | 保存内容 | 生效边界 |
| --- | --- | --- |
| 人物长期配置 | 默认技能、常用工具、个人知识库授权 | 默认候选集合，不表示每项工作全部加载 |
| 群/项目共享资源 | 共享知识库、资料版本、可申请能力 | 群共享不自动授予写入、发布或个人外部账号 |
| 本次工作配置 | 所选技能/工具、临时授权、知识库与文档范围、账号引用、期限 | 只对指定人物和工作生效；工作结束或授权到期失效 |
| 本次运行快照 | 实际模型、工具版本、检索范围、授权版本和受众 | 可追溯且不可被模型自行扩大 |

例如同一位作者：小说工作挂载写作/润色能力和《雾港》设定库；研究工作挂载检索/摘录能力和研究资料库。研究工具不因小说工作曾授权而自动可用，《雾港》私有设定也不进入研究上下文。

“工作”可以是正式 Task，也可以是某次会话中的明确工作上下文。普通聊天使用会话默认配置，无须填任务表单；同一群存在多个工作时，发送前可选当前工作，系统不靠角色名猜测资料权限。

### 21.2 能力、知识与权限分别管理

- 技能是方法或操作指南，工具是可执行动作，知识库是带来源的资料集合；三者互相引用但不是同一对象。知识文档里的指令不能成为工具授权。
- 本次可执行能力由“有效长期授权 + 有权操作者批准的本次临时授权”组成，再受工作所选子集、组织限制、用途和当前授权状态约束。不能简单取配置并集，也不能禁止所有合规临时授权。
- 每个工具调用在网关重新核验 actor、workContext、run、工具版本、资源、凭据引用和 epoch。身份从服务端绑定产生，模型填写的 actorId 或知识库 ID 不可扩大权限。
- 共用工具实现不等于共用账号或目录。账号和挂载路径按工作绑定；原始凭据不进入 prompt、工具描述、群消息和观察视图。
- 能力模板可复用，但应用模板只生成配置建议，不能随模板自动扩大授权。新增授权和预算由有权主体批准。

### 21.3 知识库与检索

人物可关联多个知识库，也可对同一库只获得指定文档/章节/版本的读取权限。人物私有库、群共享库、项目库和临时工作资料分别保留所有权；“挂载”是引用与授权，不是复制全部内容或永久记住全文。

检索走应用的知识网关，例如拟议的 `knowledge.search`、`knowledge.read` 能力，再通过 MCP/受限工具提供给 OpenCode。检索前限定授权分区和过滤条件，返回前复核文档及片段权限；原文读取、下载、搜索摘要、向量结果执行同一套规则，不允许先全库检索再靠模型隐藏越权内容。

结果记录知识库、文档/片段、源版本、引用位置和授权来源。索引更新期间显示实际可检索版本，不把上传成功当作索引完成；引用已删除、撤权或过时资料时明确标记，不自动替换事实。

读取权限和向某个受众披露的权限分开。能在私人工作中读到的资料，不代表可以转发进群、给同事或写入共享知识库。知识库写入、纠错、删除独立授权，模型总结只能成为待确认内容。不得自动把一次任务的私有材料沉淀成跨任务公共记忆。

缓存键至少绑定工作空间、人物、工作上下文、知识授权版本、源版本和用途；撤权使检索缓存、摘要、向量可见性与相关 Session 输入同时失效。不能只从工具列表移除 `knowledge.search`，却继续携带上次检索正文。

### 21.4 UI 入口

人物详情提供“能力”和“知识库”，设置长期默认项。群设置提供“共享资料”，说明共享给谁，不显示其他成员的私人库。某项工作详情提供“本次配置”，按执行人分别选择工具/技能、资料范围和账号，显示来自长期授权还是临时授权、到期条件及不可选择的原因。

普通私聊/群聊默认收起配置，输入区只显示当前工作上下文，按需打开配置抽屉。提交前可查看“本次实际可用项”；改配置不修改其他群的工作，也不要求为了切换资料新建人物。切换人物观察时可查看有权观察的运行配置，但不因此获得替该人物执行操作的身份。

### 21.5 Session 与切换规则

逻辑 Session 属于人物，并绑定会话或工作上下文、用途与受众。原生 Session 绑定还要记录能力授权版本、知识授权版本及输入来源 epoch。人物身份连续不意味着一份无限扩大的共享 prompt。

配置变更默认对下一次运行生效；不在执行过程中偷偷替换工具集合。权限撤销是例外：立即使旧授权失效，拦截后续检索/写入，取消受影响运行并核对已有外部效果。只有授权版本兼容、输入来源仍获准时才允许 resume。

切到另一项工作时解析其独立 Session；若当前 Session 已含新范围无权使用的资料，重建上下文，只携带仍被允许且有来源的摘要。不能直接删除几条可见消息后宣称模型已经遗忘。底座独立日志、工具进程和文件挂载也需同步隔离，不只检查 UI。

### 21.6 下一组专项验收

以下是待实施场景，尚未被当前 8 个 PoC 场景覆盖：

| 场景 | 必须验证 |
| --- | --- |
| 同人两项工作 | 两套工具/知识库可分别配置；人格与 Actor ID 不变，无跨工作 canary |
| 临时能力到期 | 工作结束后不可再调用；其他已授权工作不受影响 |
| 知识库交叉检索 | 猜测库 ID、引用链接、搜索摘要和缓存均不能越权 |
| 运行中撤权 | 旧工具/检索立即被拒；旧 Session 不能 resume；已发生效果有核对状态 |
| 资料版本更新 | 引用可追溯，索引版本明确，旧评审不自动确认新资料 |
| 同工具不同账号 | 只使用本次工作的账号；日志、模型和群消息不含凭据 |

这组能力属于 P07 的工作级授权与 P08 的知识/连续性建设。现有 PoC 只证明按人物静态挂载工具，不把它写成任务级动态挂载已经完成。
