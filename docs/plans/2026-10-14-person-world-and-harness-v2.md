## 当前确认：IM 主体、独立能力与底座边界

最新选型状态：用户同意继续使用 OpenCode，首版确定为服务式 Harness。CLI 只启动 headless 服务，正式适配器计划通过 SDK 调用；已完成的独立 PoC 直接调用 HTTP API，未接生产业务。Pi 保留后续替换选项，其他项目的 Pi 经验不等于本仓库集成。详见[本地验证报告](2026-10-15-opencode-im-poc.md)。

用户明确确认：这是类似 DeepSeek-Bot 的 IM 应用。典型入口是创建一个小说创作群，邀请已有的编剧、作者、编辑等人物，在群里提出要求；人物讨论、形成各自分工、调用自己挂载的能力，再通过群聊或私聊继续协作。不是启动小说项目后由固定状态机依次调度角色。

- 人物长期独立存在。人格、专业定位、模型选择、能力挂载与聊天记录分别管理，不把人物等同于某项工具或某个阶段。
- 群是沟通场所，不是 workflow 实例。可以只讨论，不创建正式任务；任务、成果、审批只是需要时出现的辅助对象。
- 能力库独立于人物。工具/技能可按不同权限挂给不同人，同一工具不需要为每个人复制实现；资料和实际操作范围仍按人及本次用途核验。
- 小说能力后续作为领域工具接入。作者调用写作，编剧调用故事/章纲设计，编辑调用审稿；没有小说工具时，IM、人物和普通讨论依然成立。
- 用户在其他项目尝试过 Pi Harness 与模型 Provider 配置。这是可参考的接入经验，不代表本仓库已经集成，也不要求迁入其他项目的代码。

- 同一人物可按不同工作临时挂载不同能力及知识库。长期人格与身份不变，能力/资料授权按人物、工作、用途及受众分别核验；普通聊天可使用会话上下文，不强制先创建 Task。详见[详细设计第 21 节](2026-10-14-person-world-detailed-design.md#21-按工作挂载能力与知识库)。

## 1. 产品模型

产品是一套由真实用户和长期 AI 成员共同参与的协作环境。AI 成员在系统中是完整参与者，不只是某个阶段的提示词，不属于临时创建它的另一个 Agent，也不随项目结束消失。

“映射现实世界”落实为身份、关系、信息来源、承诺、资源、权限和工作结果之间的真实因果关系。没有收到的消息不能声称已读，没有执行的动作不能声称完成，没有参加的私聊不能自动知情。人格表现可以丰富，但能力、经历、社交记录必须有来源，不编造已经发生的生活和工作。

每位成员拥有：

| 现实对象 | 产品对象 | 说明 |
| --- | --- | --- |
| 身份与个人档案 | Actor + AgentProfile | 姓名、头像、背景设定、性格、价值偏好、沟通方式、人格版本 |
| 专业能力 | Skills / CapabilityGrants | 会做什么、可用工具、权限、经过验收的作品 |
| 联系人 | Contact / Relationship | 与谁协作过、可联系谁、联系限制、与特定人的已确认约定 |
| 私聊与工作群 | Conversation + Membership | 人与 AI、AI 与 AI 都可私聊，也可以进入多个群 |
| 收件箱 | Inbox / DeliveryReceipt | 收到的消息、请求、问题、交付、邀请，不等于模型上下文 |
| 工作台 | Commitments / Tasks / Calendar | 接下的工作、依赖、截止时间、当前注意力、待回复事项 |
| 个人资料 | PersonalAssets / Notes | 自己的草稿、笔记、获授权资料、成果记录 |
| 经验与记忆 | Memory | 有来源、可更新、有使用范围和披露规则 |
| 当前工作上下文 | LogicalSession | 这个人在当前私聊、群或任务中使用的连续工作记录 |
| 执行工具 | HarnessBinding | 底层模型运行与工具执行；可替换，不定义人物身份 |

首版不模拟银行、住址、生理需求等与工作无关的系统；可以记录人设中的背景设定，但须区别于已发生的工作事实。浏览器身份、外部服务账号等是按需授权的个人资源，不默认共享真实用户的登录态或凭据。

## 2. 与 V1 的实质差异

| V1 假设 | V2 调整 |
| --- | --- |
| 私聊主要指用户找成员 | 任意被允许的两位参与者都可私聊，包括 AI 与 AI |
| 用户是所有会话的隐含中心 | 用户只是某些会话中的参与者；作为系统所有者另有观察权限 |
| 负责人召集所有工作 | 负责人是一位被赋予协调职责的成员；其他人可独立接单、协商与请求帮助 |
| 成员有一页资料 | 成员有完整个人工作空间，包含消息、联系人、群、工作、资料、记忆、Session |
| 视图固定在用户一侧 | 全局切换观察对象，显示该成员的完整可见世界 |
| AgentSession = 成员 + 会话 | Session 增加个人工作、会话、任务等用途，并与底层运行记录分离 |
| 从传输层开始自建工具循环 | 优先集成开源 harness，自己实现身份、协作、授权与业务状态 |
| 工厂 DB 是所有内容的唯一存储 | 工厂 DB 是业务事实权威；harness 原生日志可独立持久化，通过映射、回执与备份管理 |

所有对等参与者使用同一套消息、邀请和成果规则。对等身份不意味着权限相同：群管理员、项目负责人、作者、审阅人和系统所有者各有明确授权。

## 3. 一次符合现实协作的工作

示例：你邀请林岚、陈墨、周宁创建“雾港来信”群。

1. 你在群里提出首章目标。消息进入群时间线，并投递给当前可见的成员。
2. 林岚根据负责人的职责提出分工。陈墨接受写作，周宁接受审校；未接受之前只是请求，不伪装成双方已达成承诺。
3. 陈墨发现人物动机有疑问，单独私聊林岚。双方私聊出现在两人的会话列表中，不自动出现在你和周宁的消息列表中。
4. 林岚回答后发现会影响已确认设定，在项目群提交变更建议，而不是用私聊结论悄悄改正式设定。
5. 陈墨在自己的任务工作区写作，周宁可以并行准备审校清单。成员忙碌时仍能收件，但不必瞬间答复每条消息。
6. 陈墨把正文 v1 交付到群中，周宁针对 v1 审阅。修改产生 v2，v1 的审阅不会被当作 v2 已通过。
7. 验收者确认 v2。小说适配器执行既有质量校验和正式事实写回，任务才完成。
8. 项目归档后，个人关系、许可保留的经验和作品记录仍在。群可归档，人物不销毁。

用户切到陈墨视角，可以看到他与林岚的私聊、所在群和工作；切到周宁视角，不会在周宁的上下文中凭空出现那段私聊。系统所有者能够观察，不代表所有成员彼此全知。

## 4. 三种视角与操作权限

### 4.1 我的视角

以真实用户的 Actor 为观察对象，只显示自己参与的私聊和群，以及有权查看的项目。AI 之间的私聊不混进我的收件箱。需要我批准、回答或验收时，通过明确消息或待办送达。

### 4.2 成员视角

全局身份选择器显示“我的视角 / 林岚 / 陈墨 / 周宁”。选择陈墨后，进入陈墨的个人空间：

- 消息：谁给他发了私信，他给谁发过消息，各会话的待处理情况。
- 群组：他加入的群、职责、加入时间和可见历史起点。
- 联系人：协作对象、联系权限及双方有出处的工作约定。
- 工作：接下、发出、等待和完成的工作；不是整个系统的任务清单。
- 资料：他的草稿、可用资源和已交付成果，显示所属人和共享范围。
- 记忆：人格配置、个人经验、会话约定、来源和保留规则。
- Session：正在使用或归档的工作上下文、运行状态、模型与工具记录。

常驻标题“正在观察：陈墨”，提供“返回我的视角”。观察模式默认只读。查看不会触发模型运行，不推进成员的已处理水位，也不自动发送已读回执。

### 4.3 管理视角

系统所有者可以查看所有 AI 成员、跨成员任务和运行诊断，并进行授权、暂停、停用和迁移。管理员查询不能复用为 Agent 的检索接口。

“切换视角”不等于“以这个人身份发言”。首版从观察界面发起沟通时，返回自己的身份；后续如增加人工接管，必须显式启用、暂停该成员相关执行、取得写入租约，并在消息中记录实际操作者与代发身份，不能伪造自主发言。

首版范围是所有者管理自己创建的 AI 成员。未来接入其他真实用户或第三方拥有的成员时，不能沿用“所有者可查看全部私聊”的默认策略，须重新定义双方隐私与审计权限。

## 5. UI 交互

### 5.1 桌面布局

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 工作空间       视角：陈墨 ▾       正在观察             返回我的视角 │
├──────┬───────────────────┬─────────────────────────┬────────────────┤
│ 消息 │ 陈墨的会话        │ 与林岚的私聊            │ 会话信息       │
│ 群组 │ 林岚       待回复 │ 陈墨：这个动机有个疑问… │ 参与者         │
│ 联系 │ 周宁              │ 林岚：我的建议是…       │ 相关工作       │
│ 工作 │ 雾港来信 · 创作组 │                         │ 已共享资料     │
│ 资料 │ 活动策划组        │                         │ 陈墨的 Session │
│ 记忆 │                   │                         │                │
│ 会话 │                   │ 只读观察状态            │                │
└──────┴───────────────────┴─────────────────────────┴────────────────┘
```

导航中的“会话”在正式文案中可用“运行会话”以免与聊天列表混淆。消息视图继续采用姓名、时间、正文和必要交付卡，不把所有工具调用都当作群发消息。

个人视角与管理员总览共用组件，不通过创建多套相互独立的前端模拟多人。所有请求携带明确观察对象，服务器决定可返回的数据。

### 5.2 切换与定位

1. 点击全局视角选择器，按姓名/专长搜索成员，显示真实工作状态。
2. 切换时取消上一视角订阅和未完成读取，按 Actor 隔离缓存、草稿与定位状态；迟到响应不能落入新视角。
3. 保留各视角上次打开的页和会话位置；首次进入打开该成员收件箱。
4. 从消息头像选择“观察此成员”，可跳到他在当前会话中的视角；无权限不返回会话名称、预览或未读数量。
5. 从任务负责人进入其个人工作台，再沿来源链接回到公开群消息。
6. 多人私聊记录是同一份公共会话事实，各参与者拥有自己的收件、处理和 UI 偏好；不能复制成两份彼此漂移的聊天历史。

### 5.3 消息与工作状态

消息状态区分已持久化、已送达、已进入工作上下文、已回应。对用户可简化为“已发送 / 已送达 / 已处理”，失败展示重试入口。不用打字动画代替真实执行状态。

个人工作状态区分空闲、处理消息、执行任务、等待他人、等待授权、暂停和离线。离线成员仍可收件，恢复后根据队列处理。联系人头像状态来源于运行记录，不随机模拟。

群负责人汇总进展，但其他成员仍能提出问题、不同意见或帮助请求。普通群讨论不要求每人都发言；任务验收与外发审批才需要结构化操作。

### 5.4 Session 检视

会话详情中显示“陈墨在此会话的 Session”，群管理员总览可列出多个成员的 Session，个人视角只展示观察对象的。

列表字段：用途、关联会话/任务、模型、人格版本、状态、最新输入水位、最后活动、用量、是否发生压缩/重建。详情显示已提供输入、工具调用与结果、生成的可见文本、可读的执行摘要和出处。

不把供应商不提供的内部推理伪装成可查看的“真实思想”。输入或工具结果含密钥时必须脱敏。管理员才能执行暂停、恢复、诊断导出；普通成员不能用 Session 检视接口窥看同事。

### 5.5 手机与其他状态

手机顶部始终保留当前观察对象，底部入口为消息、工作、成员、更多；列表、聊天、详情逐级进入。只读观察不弹出输入键盘。长名称、断线、授权撤销、成员离群、消息待处理和 Session 损坏均有明确界面状态。

V1 交互预览仍只是用户视角样例。另已补充人物视角交互样例，覆盖四个观察对象、各自会话列表、同一段双方私聊、只读观察及本人发消息；其工作/资料/记忆/运行会话页面使用虚构数据。样例检查不代表本节后端权限、调度与真实 Session 已实现，范围见[详细设计](2026-10-14-person-world-detailed-design.md)。

## 6. 对等通信与工作制度

### 6.1 联系与建群

Actor 可以是 human 或 ai。两人的私聊使用同一套创建和投递服务。成员可以在允许联系的范围内主动找同事，不需要把每次内部沟通交给用户批准；跨组织、外部账号、新资料共享等另行授权。

人可以加入多个群，群可以没有项目。加入群与获得整个项目资料权限不是同一件事。邀请、接受、拒绝、离群和群管理员变更有记录；被邀请但未接受的成员不假装已参与讨论。

首版私聊是两人会话，以 workspace + 排序后的两个 Actor ID 唯一定位。群使用独立 ID，不因改名或更换负责人而创建新会话。

### 6.2 信息投递与注意力

公共消息按会话序号落盘，为符合可见范围的接收者生成各自的投递记录。所有人可收到群消息，不代表所有人立即调用模型。

明确点名、直接问题、已承诺任务的依赖变化、需要决定的事项触发唤醒。普通群消息可合并到成员下一次读取增量；成员可以按工作方式主动参与。调度机制节约运行，不篡改“谁知道什么”的事实。

不能让一个全知的总 Agent 读取所有私聊、替所有成员编造回复。运行调度器可以看任务状态以分配容量，但模型协调者只有自己的成员权限。

### 6.3 承诺与执行

聊天可以提出请求；接收方接受后形成工作承诺，再产生可追踪任务。简单问题不需要强制创建任务。任务至少有负责人、目标、来源、截止约定、验收标准和状态。

成员可以澄清、协商交付范围、因能力/权限/负载拒绝、建议转交。默认范围内自主工作，关键成果按约定验收，外部高影响动作走审批。

群负责人不是不可见的超级用户。一个成员在项目 A 做负责人，在项目 B 做作者，权限随关系与任务变化，人格身份不改变。

### 6.4 约束与终止

工作符合信息与责任流，不要求人为加入打字延迟或无意义上下班表演。安静时不持续空转调用模型。主动提醒和定时工作必须是被授权的待办或计划事件。

沿用 V1 的轮次、预算和委派深度保护，但这些是系统保护上限，不是每段对话必须执行的流程。AI-AI 私聊同样计入预算，完成/无新进展/达到上限后收束，不能互相唤醒无限寒暄。

## 7. Session 模型

### 7.1 五种不能混为一谈的对象

| 对象 | 生命周期 | 用途 |
| --- | --- | --- |
| Actor | 长期 | 这个人是谁，改名换模型也不换身份 |
| Conversation | 长期 | 哪些人之间发生过什么可见交流 |
| LogicalSession | 工作连续期 | 某个 AI 在某种用途下的私有工作上下文 |
| HarnessSession | 由底座管理 | 具体模型消息、工具结果、压缩与执行恢复记录 |
| Run / Attempt | 一次执行 | 某条输入或一组任务触发的运行、重试和结果 |

一个群有一份公共时间线，但可有 N 位 AI 各自的 LogicalSession。两位 AI 私聊有一份公共时间线和两边独立的 Session；真实用户没有模型 Session。

### 7.2 每个成员的个人连续性

每位 AI 有个人工作台与持久 inbox；按需分配一个 `personal` LogicalSession，用于整理待办、复盘或规划。它不是永远运行的大脑进程，也不把全部私聊原文反复塞进同一个上下文。

另外维护 `conversation` 和 `task` Session。个人记录、记忆、关系和成果是跨 Session 连续性的来源；换上下文不等于换人。默认每位成员同一时刻一个注意力/执行租约，不同成员可并行。后续开放并发时，应展示同一成员的多项工作与冲突控制，而不是默认为多个互相不知道的分身。

需要等同事回复时，任务进入等待，释放可调度容量。同事回信作为新事件唤醒相关 Session，不把工具调用永久挂起等待另一位成员，也不占满 worker 导致互等死锁。

### 7.3 Session 映射

```text
actor:chen
  personal session
  conversation:dm(chen,lin)  -> logical session S1 -> harness session H1
  conversation:novel-group  -> logical session S2 -> harness session H2
  task:chapter-1            -> logical session S3 -> harness session H3
```

不同人物不得共享同一个底层 Session 后只切换 system prompt。相同人物的不同会话也不默认复用一个无边界的底层 Session。底座中的临时 subagent 是执行辅助，不自动成为通讯录里另一位长期成员。

同一逻辑 Session 同时只有一个活动 harness 绑定。压缩一般由所选底座负责；损坏重建、换底座或不兼容升级时新增 `session_epoch`，保留旧日志并记录所使用的交接摘要和事实引用，不承诺原生上下文无损转换。

### 7.4 输入与发言

对陈墨的运行，林岚和其他人的消息都是带 sender、conversation、sourceSeq 的外部输入，不得伪造为陈墨自己的 assistant 历史。由陈墨本人输出并提交的公开消息才回到陈墨的发言记录。

一轮工具结果、私有草稿、Session 压缩摘要不自动发到群。发言须明确目标会话，由 `send_message` 等受控工具提交，或由运行请求预先固定回复目标；系统不将任意最终文本广播给所有联系人。

观察接口只能读取日志与快照；打开 Session 不执行 `prompt`，不调用可能写入修复事件的恢复接口。真正恢复由拥有租约的执行服务负责。

## 8. 记忆、资源与隐私

独立人格需要有延续的经验，但“记得”与“能向任何人披露”不能混为一谈。

每条记忆至少保存 owner、来源、使用目的、来源访问权限、可披露对象、创建与撤销时间。人格配置和已确认的通用方法可跨工作复用；具体项目设定、私聊承诺和敏感材料按范围保留。

跨会话连续性通过可用摘要和授权检索实现。不能把成员的所有秘密灌进每次群聊 prompt，再只靠一句“请保密”防泄露。检索时限制用途和来源，发消息/共享成果时检查目标；高敏信息不进入无权披露的运行上下文。

个人工作目录只是组织方式，不是安全隔离。文件、笔记、检索索引、浏览器 profile、连接器授权必须分别归属；底层执行环境只挂载当前获授权输入和输出目录。不同群共享正式文件时通过版本与锁处理，不通过共享任意可写 home 目录。

管理者可以观察自己拥有的 AI 的资料，但 Agent 不继承管理者的观察权限。首次接入外部账号时，UI 要明确资源属于谁、哪些任务可使用，凭据引用与明文分离。

## 9. 技术分层与 Harness 边界

```text
IM 与个人视角 UI
        |
协作 API：身份 / 关系 / 会话 / 收件箱 / 任务 / 资料 / 观察授权
        |
factory.sqlite：业务事实 + outbox + 投递/工具幂等账本
        |
成员调度器：注意力租约 / 预算 / 唤醒 / 等待 / 恢复
        |
Harness Adapter：Session 绑定 / 输入投递 / 事件映射 / 停止 / 审批
        |
候选 Harness：OpenCode 服务式 / Pi 嵌入式，暂不锁定
        |
独立接口 A：Provider 配置 / 模型目录 / 每个人物的模型绑定
独立接口 B：能力库 / 人物能力授权 / 受限工具网关
        |
模型服务与隔离工具环境；小说是可选能力包
```

自己开发的是“这些人如何存在、联系、承诺和交付”，复用的是模型工具循环、上下文压缩和底层 Session 机制。不把现有小说状态机升级成控制所有人物生活的总流程。

Harness 不能成为业务任务的第二位调度者。业务层决定谁该运行、给什么输入和什么权限；底座决定一次运行内部如何调用模型与工具。底座的 todo 或 subagent 结果不会自动替代正式承诺、验收或成员身份。

候选比较和原生 API 限制见配套调研。OpenCode 与 Pi 都不定义人物身份或群工作流；不同的是服务化接口与嵌入式控制的接入方式。最终只选一个默认底座，并验证本产品需要的多人物、群内独立 Session、模型配置、停止与恢复，不因多模型或自定义工具需求就断言必须选 Pi。

Provider 管理与能力管理是平行配置：Provider 决定可调用哪些模型，能力授权决定可以做哪些动作。所有者配置 Provider 和凭据引用，人物独立选择 `providerId + modelId`；换模型不换 Actor、不清除聊天与经历，也不自动增加工具权限。原生上下文能否复用另行校验。具体界面和运行规则见详细设计第 20 节。

| `collab_assets` / `collab_memory_sources` | 所属成员/项目、来源、访问与共享范围、版本 |
| `collab_observer_audit` | 管理者观察对象、接管/代发、导出和敏感管理操作 |

约束：所有关系必须位于同一工作空间；DM 人对唯一；消息不允许由客户端任意伪造 sender；AI 不能通过修改参数成为人类用户或系统所有者。

新增接口语义：

- `GET /api/collab/perspectives`：当前操作者可观察谁。
- `GET /api/collab/actors/:id/inbox|conversations|contacts|work|assets|sessions`：经观察授权后的个人投影。
- `POST /api/collab/conversations/direct`：创建或返回两人私聊，校验发起者联系权。
- `POST /api/collab/conversations/:id/messages`：身份来自登录上下文或可信运行，不接受随意代发。
- `GET /api/collab/sessions/:id/inspection`：只读、脱敏，不唤醒模型。
- `GET /api/collab/events?perspectiveActorId=...`：按操作者与观察对象双重过滤的事件订阅。

这些是产品接口草案，不是声称上述外部 harness 使用相同 API。拒绝访问时不得先返回标题、预览、未读数或文件路径再隐藏正文。

## 11. 持久化与故障处理

业务层 SQLite 保存身份、会话、公开消息、承诺、任务、授权和成果的权威状态。底座原生日志可以保存模型历史和工具执行细节，不直接写入业务表，也不成为另一个正式群聊存储。

因为外部 harness 与工厂 DB 无法天然共享事务，使用如下边界：

1. 业务命令、投递记录和 outbox 同事务提交。
2. 适配器记录 invocationId、外部输入 ID、Session 绑定与请求水位，再投递。
3. 底座收到不等于任务完成；可见工具事件、公开消息提交和成果验收分别确认。
4. 所有业务写工具以服务端运行身份、租约与幂等效果 ID 提交；重试不重复发信、建任务或验收。
5. 断线后先读取原生 Session 与已确认效果。无法判断外部动作是否执行时标记待核对，不能盲目重放。
6. UI 的事件重连使用本项目的持久事件序号，不假定底座 SSE 一定保留可重放事件。
7. 备份必须同时涵盖 factory DB、原生 Session 存储、资料版本和映射清单。记录一致的检查点；只备份业务库不能保证恢复成员工作现场。

每个逻辑 Session 串行写入；每位成员默认一个注意力租约。取消优先通过底座正式取消接口，等待其收束，再释放租约；进程失联不能直接视为动作已停止。停止等待的任务要清理后续唤醒条件，但保留已交付记录。

## 12. 与小说项目融合

原有六个固定角色不能直接通过改名成为六个“已有真实历史”的人。新人物由用户创建或确认，旧消息保留原作者标签与历史来源。

小说是群里可以共同完成的一类工作，规划、写作、审校、RAG、Canon 等作为领域工具。工具使用任务负责成员的模型/权限绑定，结果进入其工作记录；正式设定、章节检查与写回门禁不变。

新 IM 路径优先按故事设计、写作、审阅、资料与版本操作拆出能力，由人物按协作需要调用，不以整条旧流水线驱动群成员。旧流水线可保留在明确标注的兼容入口，但不作为新群的默认工具，也不能把它内部的多角色输出伪装成群里不同人物的发言。

旧项目的执行所有者仍须互斥：旧 autopilot 与新协作系统不能同时推进同一小说。停旧任务、确认状态、迁移映射、切换租约后再启用新执行。回退保留新增成员和沟通记录，不能随意恢复数据库快照抹掉成员的新经历。

## 13. 实施顺序

### M0：底座接入与契约验证

用户的 Pi 经验来自其他项目，本项目仍需要独立接入与验证。先明确 OpenCode/Pi 接入代价与所选版本，再验证三成员、两人私聊、群内各自 Session、多 Provider 的人物绑定、取消与恢复。IM 壳、对等消息和能力挂载契约可同步设计；准入测试不替代 IM 产品目标，也不以重新实现通用 Harness 为开发主线。

输出冻结版本、能力矩阵、原始测试记录、资源占用、适配器决策，以及对应备份/升级方式。试验详情见调研文档。现有 GitNexus 索引需在运行代码改造前刷新，并逐符号分析影响；本次只改设计文档。

### M1：人物、对等私聊与只读视角

实现 Actor、AgentProfile、联系人、任意允许双方的私聊、成员收件箱和视角切换。先用可控假模型验证投递，不用一套用户会话列表假装各成员的列表。

验收：陈墨和林岚能独立互发私信；两边看到同一条消息；周宁的个人投影没有该私聊；所有者切换观察可查看但不会触发已读或调用模型。

### M2：独立工作与群协作

接入已选底座、个人/会话/任务 Session、真实工具、成员租约、工作接受/拒绝、主动联系、群邀请和任务依赖。

验收：陈墨遇到问题私聊林岚，等待期间释放容量；林岚答复后陈墨续接原任务，用户无需充当每次消息中继。

### M3：资料、记忆、可靠性与权限

实现资料所有权、共享、版本验收、跨会话经验、原生 Session 备份恢复、预算、停止/重试和诊断。隔离与幂等是上线门槛，不拖到最后补。

验收：故障后无重复公开发言/交付，成员之间的文件和秘密隔离；观察者只读检查无副作用。

### M4：小说迁移与正式交付

将一个旧小说和一个新小说接入人物团队，完成首章规划、作者交付、编辑审阅、验收与 Canon 写回。通过后才切换默认首页并推广迁移。

本次扩大了产品范围。V1 的 10–14 周估算不直接沿用，也不能把引入开源 harness 等同于立刻省去全部开发。先为 M0 安排约 5 个工作日的时间盒，实际由版本兼容、模型访问和隔离环境就绪情况决定；以试验结果重新估算 M1–M4。

## 14. 必须通过的场景

| 场景 | 通过条件 |
| --- | --- |
| 双向 AI 私聊 | 双方独立 Session、同一公共历史，任何一方可以合法发起 |
| 视角切换 | 会话/群/资料/未读按 Actor 变化；旧订阅和迟到响应不串到新视角 |
| 只读观察 | 查看不标记 Agent 已处理，不唤醒，不以观察对象身份发信 |
| 群知识边界 | 非参与者不可读；后来加入者按历史策略可见；离群立即撤销后续访问 |
| 个人连续性 | 改名、换模型、关闭/恢复 Session 后身份、关系、承诺与授权记忆保留 |
| 私有资料 | 同机器不同成员不能靠路径、shell、检索或 raw harness API 越权读取 |
| 工作真实性 | 接受/拒绝、等待、交付均有事件，不能靠生成一句“完成”改变正式状态 |
| 同事求助 | 挂起任务不占满调度槽；回复唤醒正确 Session，无互等死锁 |
| 并发与重试 | 多成员并行，同成员默认串行；断线重试不重复发言或重复副作用 |
| 停止与审批 | 可停止指定成员而不杀死其他成员；拒绝审批不会换路径偷偷执行 |
| 不可知副作用 | 崩溃发生在外部工具提交之后时，先核对再恢复，不自动复制动作 |
| Session 检查 | 状态、来源、模型、工具可见；不虚构隐藏推理，不显示密钥 |
| 小说闭环 | 旧事实与门禁保留，新旧调度所有权互斥，审稿与验收绑定具体版本 |

这些是实施验收要求，尚未执行。当前已完成的是设计修订与官方资料/关键源码调研，不是底座集成或生产性能验证。
