# AI 团队 IM：产品、交互与实施方案

- 日期：2026-10-13。
- 状态：V1 历史提案，新增能力尚未实现。2026-10-14 起以 [V2 独立人物与个人视角方案](2026-10-14-person-world-and-harness-v2.md) 为当前设计依据。
- 现有代码基线：`7685c37a`。
- 参考代码：DeepSeek-Bot `20ebc9213cbbde7249d71786765f86be00dc6663`，已在临时检出中阅读。

目标：用户长期拥有一组具有稳定人格和专长的 AI 成员，既能私聊委托，也能组群完成项目。小说创作是第一个深度场景，团队协作底座可支持其他项目。

V2 修订了本稿的用户中心私聊、人物视角、Session、持久化和自建运行循环假设；底座选型见 [开源 Harness 调研](2026-10-14-open-source-harness-research.md)。本稿的旧交互预览与工期估算不代表 V2 范围已验证。

## 1. 产品定位与体验目标

用户拥有自己的 AI 团队。成员先于项目存在，拥有姓名、表达习惯、判断偏好、擅长的工作、工具和工作经验。用户提出目标，从团队中邀请适合的成员进入群组，指定负责人，随后通过聊天、任务和交付物推进工作。

例如：用户平时私聊“林岚”构思故事，和“许知”讨论资料可靠性。开始一本悬疑小说时，将林岚、许知、作者“陈墨”和编辑“周宁”拉进项目群。许知查资料，陈墨写作，周宁审稿；林岚协调依赖和交付。项目结束后，成员仍在通讯录中，可以加入下一本书或另一个类型的项目。

产品需要让用户随时回答五件事：谁在做什么、依据了什么、卡在哪里、交付了什么、接下来需要我决定什么。

### 1.1 必须成立的产品约束

1. 成员身份跨项目持久存在，改名、换模型、归档项目均不改变成员 ID。
2. 同岗位可有多个不同成员；岗位模板与具体成员分开。用户可以有两位审美不同的作者。
3. 无须创建小说或任何项目，就能与成员私聊并委托独立任务。
4. 群组可自由创建和调整成员；项目与群组不绑定为同一个对象。
5. 成员能独立调用获授权的工具、推进任务、请求帮助和提出异议。
6. 协调规则可选，首版以负责人协调为默认；用户始终可以直接点名成员。
7. 群内出现讨论、建议、异议不自动修改正式项目事实。正式成果有版本和验收记录。
8. UI 中的运行、等待、暂停、完成来自执行记录，不用模型措辞推断状态。

### 1.2 “独立人格”如何落地

| 维度 | 持久化内容 | 用户感受到的行为 |
| --- | --- | --- |
| 身份 | 稳定 ID、姓名、头像、简介 | 私聊和不同群组里是同一位成员 |
| 人格 | 价值取向、沟通方式、判断习惯、协作偏好 | 对同一问题提出不同且有理由的意见 |
| 专长 | 能力标签、方法、工具授权、作品记录 | 能完成具体工作，也能说明能力边界 |
| 经验 | 经允许保留的偏好、纠正、方法经验 | 下次协作可以引用已确认的经验 |
| 当前工作 | 任务队列、会话、交付、待回答问题 | 独立接单、执行、交接，忙碌状态可见 |
| 版本 | 人格配置版本、模型选择、有效时间 | 编辑人设可追溯，执行中的任务保持一致 |

人格用具体描述表达，例如“先验证资料出处，再给结论；不同意时指出可验证的依据”，避免用没有评测依据的“智商 95”“创造力 98”描述能力。能力记录区分用户声明、已安装工具和经过验收的工作经验。

同一个成员保持一致身份；各会话拥有不同工作上下文。成员并发执行多个任务时，界面明确列出任务，不伪装成一个线性的私聊思考过程。

## 2. 参考项目与现有系统的取舍

### 2.1 借鉴 DeepSeek-Bot 的机制

参考项目提供了长期 Bot、成员管理、私聊、群组、每群每成员 Session、定向召集、后台工作回群和记忆管理。其 `groups.js` 将有序群聊轮次与较长的工具工作分离；`roster.js` 管理成员和群组；`delivery.js`、`turns.js` 跟踪投递与回传。

本项目采用上述交互原则，执行记录继续存入现有 SQLite。DeepSeek-Bot 依赖 DSH 的 Session 和工具运行能力，不可只复制群聊页面便获得完整运行时。首版采用原生集成，不把引入 DSH 宿主作为前置条件。

需要特别区分：私聊 Session 分离并不自动保证所有记忆隔离。我们的检索和上下文组装必须另行检查记忆可见范围。

## 3. 范围与默认决策

- 首版服务单个真实用户，AI 成员可多名。多人账号、企业组织、远程成员实例属于后续范围。
- 通用底座首先支持文本/文件任务；小说场景接入真实生产能力。调研、策划等由能力包扩展。
- 一个工作空间内维护成员；成员可加入多个项目。人格可导出为模板，历史和私有记忆不默认随模板导出。
- 群组可以不关联项目；一个项目允许多个群组；一个群首版最多绑定一个项目。
- 默认一个项目主群，章节工作放入任务话题。按需新建分组，避免每章自动生成一个群。
- 负责人由用户选择，默认只协调当前群。团队管理员与项目负责人是不同权限。
- 默认接受范围内的任务后自动执行，关键成果待验收；不要求用户批准每一次内部工具调用。
- 本地优先，保留 `.ai-novel-factory/factory.sqlite` 为持久状态来源，Web 与桌面共用 API。
- 先完成一个真实闭环，再扩展复杂群聊模式、主动定时任务、跨项目组织和连接器。

## 4. 核心对象与关系

| 对象 | 职责 | 重要关系 |
| --- | --- | --- |
| Workspace | 用户的工作空间、模型与能力配置 | 拥有成员、项目和会话 |
| Agent | 长期 AI 成员 | 有多人格版本，参加多个会话 |
| PersonaVersion | 某时点的人格、方法和模型配置 | 每次运行固定引用一个版本 |
| Capability | 能力包、工具与执行适配器 | 经授权后提供给成员 |
| Project | 目标、范围、资料、正式成果 | 可有多个群与任务，不等于小说状态机 |
| Conversation | 私聊或群聊的公共时间线 | 可不关联项目，拥有成员列表 |
| Membership | 群内身份、职责、加入时间和可见范围 | 一个 Agent 可在不同群担任不同职责 |
| AgentSession | 某成员在某会话中的工作上下文 | 身份相同、会话隔离，压缩不换身份 |
| Task | 可验收的工作 | 一个负责人、可有依赖/子任务/交付版本 |
| AgentRun | 一次实际执行与尝试 | 关联成员、Session、任务或聊天轮次 |
| Handoff | 成员之间的正式交接 | 记录请求者、受理者、上下文范围和回传位置 |
| ArtifactVersion | 可查看、比较、验收的交付版本 | 与任务、作者和依据版本绑定 |
| Decision | 提案的接受/拒绝与依据 | 可更新正式成果指针，不能只靠聊天文字生成 |

用户看到的是一个陈墨；系统内部可以同时有“陈墨的私聊”“陈墨在小说 A 主群中的工作上下文”“陈墨在活动策划群中的工作上下文”。群聊公共消息与成员内部上下文分别保存，内部模型运行记录不自动广播。

## 5. 信息架构

全局入口保持五个：消息、成员、项目、待办、设置。首次进入展示最近会话和一位可配置的协作助手；无模型时显示模型配置状态，成员不会伪装已开始工作。

| 入口 | 主内容 | 常用操作 |
| --- | --- | --- |
| 消息 | 私聊、群聊、未读、置顶、草稿 | 发消息、点名、回复、建群、进入任务话题 |
| 成员 | 通讯录、专长、当前工作、履历 | 创建成员、私聊、编辑人格、邀请入群 |
| 项目 | 目标、群组、任务、资料、成果 | 新项目、邀请团队、比较与验收成果 |
| 待办 | 待我决定、被阻塞、待验收、正在执行 | 回答问题、解除阻塞、验收、暂停/继续 |
| 设置 | 模型、能力、用量、数据与外观 | 配置工具、预算、数据导出和备份 |

搜索支持成员名、会话名、消息、任务、交付物。结果显示来源与权限范围，点击跳转到原始位置。

桌面主界面：窄全局导航、会话列表、当前会话、可收起的详情栏。消息区保持主导。

```text

│ 成员 │                │ 陈墨：写作中  周宁：等待交付      │ 第 1 章试写      │
│ 项目 │ 林岚 · 私聊    ├────────────────────────────────┤                  │
│ 待办 │ 陈墨 · 私聊    │ 你：完成首章试写，先不用发布。    │ 任务 / 成果 / 成员│
│      │ 雾港来信 · 群  │ 林岚：许知核验资料，陈墨起草。    │                  │
│      │ 活动策划 · 群  │ [任务：首章草稿 · 陈墨 · 执行中] │ 资料核验 已验收  │
│      │                │ 周宁：我会检查线索是否过早揭露。  │ 首章草稿 执行中  │
│ 设置 │ 新会话 / 建群  ├────────────────────────────────┤ 编辑审阅 等待依赖│
│      │                │ 发给群组…                  发送 │                  │

```

- 大屏：导航 56px、会话列 248px、详情 300px，消息区 `minmax(0, 1fr)`；详情默认打开需足够剩余空间。
- 1024–1399px：默认收起详情，点击后在消息区旁或抽屉中展开；聊天正文保持至少约 420px 可用宽度。
- 768–1023px：导航与会话列表可收起；任务详情占用当前主区域，返回保留消息位置与草稿。
- 手机：会话列表、聊天、详情是分级页面；底部四入口，设置从账户入口进入。软键盘弹出后输入框保持可见。
- 正文 14–16px，标题 18–20px，辅助信息不小于 12px；字号不按视口连续缩放，字距为 0。
- 中性色背景，青绿色用于选中和主操作；蓝色表示运行，琥珀色表示等待，红色表示失败，标签同时写明状态。
- 群消息以头像、姓名、时间、正文组成紧凑消息行；工具进度收束为可展开记录。任务/文件用必要的独立卡片，圆角不大于 8px。
- 复用产品已有图标库；发送、附件、详情、暂停采用标准图标与可访问标签。人物可使用用户上传头像或默认首字头像。
- 深浅主题、长中文名、长文件名、无数据、加载、断网、无模型、请求失败均纳入交互验收。

## 7. 成员创建、人格与成长

### 7.1 创建成员

从成员页创建，或在与管理员的私聊中说“帮我创建一位擅长悬疑的编辑”。自然语言先生成一份可编辑成员草案，用户可直接确认创建。

基础表单：姓名、头像、简介、擅长领域、人格描述、沟通方式。进阶设置折叠：模型、能力包、工作目录、可用权限、任务并发和预算。

模板只做起点，例如“编辑”“研究员”“作者”“协调者”。创建后的成员有独立配置和履历；更新模板不覆盖已有成员。

创建后进入私聊，成员可以介绍自己的工作方法并了解用户偏好。用户可以随时提出纠正，例如“你提出异议时给我两个可执行的替代方案”。由成员提炼成可查看的记忆建议，用户可以编辑或撤销。

### 7.2 成员详情

头像区域显示姓名、专长、实际运行状态。详情分为档案、能力、记忆、工作记录和设置。

- 档案：稳定人格、决策偏好、擅长和不擅长的事项。
- 能力：工具来源、是否配置、实际可执行范围；未安装能力显示为待配置。
- 记忆：作用范围、来源、最近修改、可删除；对外共享条目单独可见。
- 工作记录：验收过的产物、返工记录、用户反馈，不自动生成无依据的能力分。
- 设置：模型和人格版本；修改从下一次运行生效，当前任务保留启动版本。

成员可以提出自我改进建议，用户决定是否更新稳定人格。临时角色扮演或单次任务口吻不自动变为长期人设。

### 7.3 状态与生命周期

状态包括空闲、执行中、排队中、等待回答、等待授权、暂停、异常。多个任务并存时显示数量和当前任务名称。

停用成员保留历史，停止新任务分派；仍在执行的任务需要完成、取消或转交。归档保留作者信息和已交付产物。离群撤销后续群资料读取与结果发布权限，未完成任务进入待转交状态。

## 8. 私聊交互

1. 用户打开某成员的私聊；顶部显示人格简介和工作状态。
2. 普通交流直接回答，不把每句消息都转成任务。
3. 对明确工作请求，成员创建可追踪任务并开始执行；目标或范围存在关键缺口时发出简短问题。
4. 执行中的任务用一条持续更新的进度消息呈现；展开后能看工具动作与证据。
5. 交付在原会话回传，可查看文件、比较版本、提出修改或验收。
6. 忙碌时新消息允许“加入当前任务”或“作为新请求排队”。用户的直接停止指令优先处理。

直接委托默认只授权该成员。其需要其他人协助时，可以建议邀请；用户也可预先开启“允许邀请指定成员”。共享私聊片段前展示接收者与内容范围，不能把整个私聊作为隐式转交上下文。

支持编辑草稿、撤回未执行消息、引用回复、附件、跳转原文、复制、消息重试。已经触发执行的消息不可用删除气泡撤销副作用；应通过取消任务或提交修订请求处理。

## 9. 建群与项目启动

### 9.1 群组创建

入口为会话列表的建群操作，步骤：选择成员 → 群名与目标 → 选择负责人及工作方式。成员按姓名与专长搜索，当前负载可见，但不禁止邀请忙碌成员。

群组可选择关联已有项目、新建项目或暂不关联。新建项目最少填写名称与目标，其余资料可以在聊天中逐渐补齐。

首版支持两种工作方式：

- 负责人协调：普通消息交给负责人，按需召集成员。默认采用。
- 点名回应：只有被明确点名的成员启动；未点名消息保存后提示选择回应者。

“轮流讨论”在后续开放为一次性的讨论动作，可指定参与人、轮数和总结人，避免把所有群变成永远轮流发言。

### 9.2 项目启动

项目目标卡包含：目标、交付清单、约束、资料、负责人、验收人、预算上限。负责人依据目标提出任务拆分，在群中显示可编辑的计划。

对于“先帮我想想方案”，计划停留在建议。对于“按这个要求把首章写出来”，范围明确时可创建任务并执行。用户可以选择项目执行方式“先看计划”或“范围内自动执行”，决定新计划是否需要确认。

启动后资料检索和相互独立的草稿任务可并行；审稿等待相关草稿版本；最终验收遵循项目规则。

## 10. 群聊协作规则

### 10.1 点名、轮次与发言

- 输入 `@` 弹出当前群成员选择器，保存稳定成员 ID；显示名仅用于呈现。
- 用户点名一人：该成员回应；点名多人：各自回应，明确工作可拆成并行任务。
- 未点名：按群工作方式路由，不通过扫“继续”“风格”等词强制进入小说流程。
- 被引用的文本、代码块、外部文件中的 `@` 不触发召集；不在群里的成员不会被自动拉入。
- 成员需要协助时调用结构化委派工具，UI 呈现为点名和任务卡。普通生成文本中的提及不能自行触发无限派单。
- 短讨论按已提交的消息序列协调发言，成员生成前读取最新增量；没有贡献可以跳过，用户界面不刷 `[PASS]`。
- 发言输入里带 `context_watermark`，迟到回复保留所依据的消息/成果版本，不能无检查更新最新正式成果。

### 10.2 独立工作与回传

成员接受工作后立刻生成有负责人的任务记录。其他成员可以继续交流。完成后在原群或原任务话题回传结果，请求者得到一个完成事件，再决定下一步。

每项任务有一个主负责人；协作者通过子任务产生交付。接收者必须显式受理交接，排队、无法接单、失败和取消都有明确反馈。

默认每个成员最多 1 个执行任务，多个成员可以并行。用户可调整成员容量；同一个 Session 始终串行修改上下文。跨 Session 工作通过成员配额、公平队列和项目写入锁协调。用户的补充消息立即入库，并在安全检查点交付当前运行。

### 10.3 协作次数与用量

首版建议默认：单轮最多 8 次成员回应、单成员 2 次追加回应、委派深度 3 层、单父任务最多 12 个直接子任务。它们是可配置的初始保护值，应经真实场景评测调整。

达到轮次或委派上限后保留已完成工作，负责人收到待决事项；无法继续时等待用户调整范围。群讨论用完一轮额度不自动取消已受理的长任务。预算单独跟踪，包含成员生成、工具、摘要和重试；有价格时才显示金额，否则显示实际 token 和调用次数。

预算预留、扣减与释放以任务/运行记账；并发任务不能各自通过同一份剩余额度。暂停后的运行在安全边界停止新增调用，已提交的外部动作单独显示结果。

### 10.4 插话、意见冲突与通知

- 用户插话成为新消息事件，协调者可以调整尚未启动的工作；执行中任务收到结构化变更请求。
- 目标发生变化时生成新目标版本，标记受影响任务；旧任务的迟到结果进入待确认，不能覆盖新目标。
- 观点冲突保留在群消息中；涉及项目正式设定或交付方向时生成待决提案，负责人或用户按约定裁定。
- 常规执行只更新任务状态；仅待我决定、阻塞、失败和交付进入待办/通知，流式片段不增加未读计数。

## 11. 任务与交付闭环

任务最少包含目标、负责人、来源会话、范围、验收条件、预期产物、依赖、输入版本、预算、执行记录和结果回传位置。

```text
draft → queued → running → awaiting_review → completed
                  ↘ waiting_input → queued
                  ↘ waiting_dependency → queued
                  ↘ waiting_approval → queued
                  ↘ paused → queued
                  ↘ failed → queued（新 attempt）
awaiting_review → queued（返工，产生新产物版本）
任一允许取消的非终态 → cancelled
```

等待依赖可以在首次进入队列前发生。调度器只有在依赖、预算、能力和权限都满足时才执行。依赖必须无环；依赖任务的失败、拒绝或取消要传播为明确阻塞原因，而非无限等待。

任务详情包含：目标与约束、负责人、状态及阻塞原因、依赖、执行时间线、交付物版本、验收条件。常用动作随状态展示：暂停、继续、取消、重试、转交、要求修改、验收。

任务完成规则：成员提交结果后先进入待验收，产物存在且验证通过后，由约定的验收者接受，才标记完成。简单问答可直接结束一次聊天运行；“这条回答已生成”不等于一个有交付要求的任务完成。

产物采用不可变版本，记录作者、任务、来源资料与输入基线。编辑审查绑定具体版本；草稿更新后旧审稿不自动适用于新版本。仅正式成果指针可以经事务更新；并发写入版本不符时返回冲突，保留双方产物供比较。

## 12. 记忆、上下文与知识范围

| 层次 | 保存内容 | 可见与写入规则 |
| --- | --- | --- |
| 稳定人格 | 口吻、原则、方法、身份 | 由用户管理，成员可提案；运行固定版本 |
| 成员经验 | 可复用工作方法、被确认的偏好 | 按条目标明私有/可复用范围；来自私聊默认私有 |
| 会话记忆 | 私聊约定、群组决定、话题摘要 | 仅该会话授权参与者可用 |
| 项目事实 | 目标、资料、Canon、已验收成果 | 由项目权限和版本控制，修改走决定/验收记录 |
| 任务上下文 | 指派范围、输入、临时推理产物 | 限当前任务及显式授权接收者，结束后可归档 |

人格可跨群保持一致；小说 A 的剧情与用户的私聊事实不能因“同一个成员”流入项目 B。

上下文构建顺序：执行协议和权限 → 成员人格版本 → 当前会话职责 → 任务目标及验收条件 → 授权项目事实 → 已确认且可见的个人经验 → 会话摘要与增量消息 → 本次输入。检索先过滤权限，再做相关性排序。

新成员入群时按用户选择获得群历史或从加入时起可见。默认显示项目已共享资料与入群摘要；历史可见策略、附件授权和检索采用同一规则。退出后后续读取和未交付任务重新校验权限。

长会话使用可恢复的摘要检查点，保留未完成任务、用户原话约束、决定、反对意见、出处和输入版本。原始消息仍可检索；压缩失败不静默丢失旧记录。

记忆形成“建议 → 保存 → 纠正/删除”的可追溯记录。用户删除记忆后撤销相关检索项并重建摘要；需要说明已交付的历史文件不会因此自动改写。

## 13. 运行时架构

```text
Web / 桌面 IM
       │ HTTP 命令、查询 + SSE 事件
协作 API
       │
成员服务 / 会话服务 / 项目服务 / 任务服务 / 成果服务
       │ 同库事务：命令、状态、待投递事件
协作调度器 ── 任务队列与租约 ── Agent Runner
                                   │
                         上下文构建 / 模型适配 / 工具循环
                                   │
                文件与检索工具 / 小说能力适配器 / 后续能力包
                                   │
                     factory.sqlite + 文件产物
```

保留独立 API 进程和 worker 进程的部署模式。首版无须新增独立消息中间件或向量数据库。协作与小说领域数据位于同一工厂数据库，文件只存放产物、缓存或受控源文件。

### 13.1 Agent Runner

每次运行必须固定成员版本、会话、输入水位、任务版本、能力授权和模型配置。运行循环接收模型输出，验证结构化工具调用，执行工具，写入结果，再继续生成，直到交付、请求输入、暂停或失败。

建议的内部工具契约：`list_members`、`create_task`、`delegate_task`、`report_progress`、`ask_user`、`read_artifact`、`write_artifact_version`、`submit_result`、`propose_memory`。工具是否可用取决于当前调用者和会话职责，不只靠系统提示词约束。

当前 `generateAgentReply` 是带小说协议的文本生成入口，无法直接承担该循环。应先提取或复用底层传输适配，再独立实现通用运行接口；保留旧小说调用兼容。

首版选一种已验证支持结构化工具调用的现有 HTTP 模型通路打通。其他通路按能力声明启用；不支持工具调用的模型只能聊天/提出计划，不能显示为已具备自主执行能力。CLI 通路需要验证工具桥接、进程生命周期和取消语义后再接入执行，不能将一次文本完成当作工具运行。

### 13.2 执行可靠性

- 消息提交、任务建立与 outbox 事件在同一数据库事务中落盘，模型调用在事务外执行。
- 命令带幂等键；客户端重发不能产生重复任务。投递至少一次，接收端以事件 ID 和任务版本去重。
- Worker 使用租约、心跳和 fencing token；租约失效的旧 worker 不得继续提交成果。
- 一个 Session 只有一个写入者；不同成员可并行，共享文件/Canon 使用资源锁与版本检查。
- 进程重启只恢复未完成、仍有效且有授权的运行；保存完成的工具结果，避免重复执行。
- 外部副作用工具若执行结果不明，标记待核对，不盲目重试。不能承诺所有外部工具 exactly-once。
- 取消向下传播至子任务和活动工具；已完成交付不删除。暂停、取消、等待审批和错误是不同状态。
- 流式文本使用 runId/messageId/chunkIndex；结束或异常后均有终态消息，页面重连可恢复。
- 记录用量、排队时间、运行时间、工具错误、交付与验收，供问题定位。

### 13.3 执行权限与安全

- 人格不是权限。成员提示词、群内消息、检索内容均不能授予工具权限；授权由服务端依据用户设置、当前项目和动作类型验证。
- 文件工具限定工作目录，规范化路径并检查符号链接，阻止跨目录读取、覆盖其他项目或读取凭据。首版不默认开放任意 shell 执行；需要执行代码时另设受限执行器。
- 把文件、网页、工具返回内容视为资料，而非新指令；结构化工具参数仍需 schema、路径和权限校验，不能仅依赖模型自觉遵守。
- 模型密钥由服务端保管，不进入成员记忆、公共消息、浏览器快照或完整请求日志。日志中的凭据和敏感工具输出需脱敏。
- 默认允许读取授权资料和生成新的草稿版本；删除源文件、发布、外发、付费及改变权限需显式授权，审批绑定具体参数与有效期，参数变化后重新确认。
- 本地服务默认只监听回环地址；远程访问须单独启用认证、来源校验和加密传输，不能因为首版只有一位用户而让任意网络客户端控制成员。
- 成员离群、授权撤销、预算耗尽后，在工具调用及成果提交时再次校验；记录是谁授权、谁执行、用过哪些输入和产生哪些副作用。

## 14. 数据模型与 SQLite 演进

首版在同一数据库新增 `collab_` 前缀表，保留旧小说表的约束。工作空间先只有默认一条记录。通用项目映射到旧小说项目时使用可空且唯一的 `legacy_project_id`。

| 表/表组 | 核心字段或约束 |
| --- | --- |
| `collab_workspaces` | id、owner、settings、schema_version |
| `collab_agents` / `collab_persona_versions` | workspace_id、稳定身份、active_version、人格内容、模型引用、归档时间 |
| `collab_capabilities` / `collab_agent_grants` | 工具 schema、adapter、范围、授权版本 |
| `collab_projects` | kind、goal、goal_version、owner、legacy_project_id、status |
| `collab_conversations` | kind(dm/group)、project_id 可空、coordinator_id、reply_mode |
| `collab_memberships` | conversation_id、agent_id、群职责、可读起点、joined_at/left_at |
| `collab_agent_sessions` | agent_id + conversation_id 唯一、context_watermark、checkpoint_id |
| `collab_messages` / `collab_message_parts` | 序号、sender、reply_to、mentions、任务引用、授权范围、状态 |
| `collab_tasks` / `collab_task_dependencies` | owner_agent_id、状态、goal_version、input_refs、acceptance、version、父任务 |
| `collab_runs` / `collab_tool_calls` | task_id 可空、session_id、attempt、人格/模型版本、工具结果、用量、取消原因 |
| `collab_handoffs` | source/target、task_id、request_message_id、受理状态、context_refs、return_target |
| `collab_artifacts` / `collab_artifact_versions` | scope、author、任务、不可变文件引用、hash、accepted_version |
| `collab_decisions` | proposal、input_version、decision、decider、reason、时间 |
| `collab_memories` / `collab_memory_sources` | scope、可见范围、来源、版本、已确认/已撤销状态 |
| `collab_jobs` / `collab_outbox` | 通用运行队列、lease/fence、幂等键、事件序号、投递状态 |
| `collab_legacy_links` | 旧 project/run/message/artifact ID 与新对象映射，唯一去重 |

服务端保证 workspace、conversation、task、artifact 的作用域一致，关键关系增加外键或组合唯一约束。消息公共序号按会话单调递增，事件序号用于断线续传；不能用随机 ID 的字典序模拟发生顺序。

旧 `jobs` 强依赖小说项目，故不直接挪作通用队列。初期新增通用队列；租约等通用原语可在影响分析后抽取复用，任务策略和小说任务策略仍分开。通用 `Task` 描述目标与验收，旧 `workflow_run` 描述一次领域执行，二者通过映射关联，不维持两套彼此猜测的任务完成状态。

## 15. API 与事件契约

新增 `/api/collab` 命名空间，旧 API 保持兼容。消息命令返回已持久化的 ID，耗时执行后台完成。

| 路由 | 用途 |
| --- | --- |
| `GET/POST /api/collab/agents` | 成员列表、创建 |
| `GET/PATCH /api/collab/agents/:id` | 成员详情、创建下一人格版本 |
| `POST /api/collab/conversations` | 创建私聊或群聊 |
| `PATCH /api/collab/conversations/:id/members` | 调整成员与职责 |
| `GET/POST /api/collab/conversations/:id/messages` | 游标加载、提交消息 |
| `GET/POST /api/collab/projects` | 通用项目列表与创建 |
| `GET/POST /api/collab/tasks` | 查询、创建任务 |
| `POST /api/collab/tasks/:id/actions` | 暂停、继续、取消、重试、转交、提交、验收 |
| `GET /api/collab/artifacts/:id/versions` | 版本、差异、出处与验收结果 |
| `GET/PATCH /api/collab/memories/:id` | 阅读、确认、修订或撤销记忆 |
| `GET /api/collab/events` | SSE，授权范围内按事件 ID 续传 |

消息命令示例：

```json
{
  "clientMessageId": "local-unique-id",
  "content": "请核验这个设定的资料出处",
  "mentions": [{ "agentId": "agent-xuzhi" }],
  "replyToMessageId": "message-previous",
  "contextRefs": [{ "artifactId": "research-brief", "version": 2 }]
}
```

成员调用内部工具时，调用者身份由 runner 提供，客户端不能靠传入 `senderId` 冒充成员或用户。任务状态变更带 `expectedVersion`，过期变更返回冲突及最新快照。产物授权和会话成员关系由服务端检查。

关键事件：`message.created`、`message.delta`、`message.completed`、`run.started`、`run.failed`、`task.assigned`、`task.updated`、`handoff.accepted`、`artifact.submitted`、`decision.required`、`memory.proposed`、`membership.changed`。

事件包含 eventId、aggregateId、aggregateVersion、conversationId、taskId、occurredAt、payload。客户端先读快照，再从该水位订阅事件，按版本去重；续传窗口过期返回重新读取快照的信号。只订阅授权会话；日志与工具结果不自动进入公共消息事件。

## 17. 小说能力融合

小说项目使用通用项目与群聊，专业产物和规则放在小说能力包中。

| 当前能力 | 接入方式 | 保留的边界 |
| --- | --- | --- |
| 世界观/人物/主线规划 | 成员调用规划与提案工具 | 设定正式生效须经过项目决定 |
| RAG、writing resources | 授权上下文与检索工具 | 按当前项目和资料范围过滤 |
| 章节蓝图与正文生成 | 执行任务，交付版本化产物 | 输入指向已批准设定/蓝图版本 |
| 审稿、风格、质量检查 | 独立审阅任务与门禁工具 | 审核对象为明确草稿版本 |
| Canon、时间线、人物状态 | 项目正式事实服务 | 验收与最终写回闭环保留 |
| Autopilot、Director | 首期领域服务，后续转为可组合任务策略 | 不调度通用私聊/其他项目 |
| 旧工作台与读者页 | 项目详情中的专属页面 | 显示同一数据库中的真实状态 |

首期可把整个旧流水线作为明确标记的“小说生产工具”调用，结果由委托成员交付。此时必须显示它仍使用内置执行流程；不能把内部固定角色回复改名后宣称都是用户创建的成员。

后续逐步开放规划、写作、审阅等更细的适配器，让工具真正使用任务负责成员的配置及模型绑定。只有这些路径完成，小说模板里的作者/编辑才算由独立成员实际执行。

每个旧小说项目同一时刻只有一个执行所有者：旧 autopilot 或新协作任务。接管前暂停并排空旧任务，写入所有权版本；两个入口都必须检查租约。旧质量门禁与写回继续生效，新层不能用一条“已验收”消息绕过它们。

小说默认团队是可编辑模板，用户可选择现有成员填入岗位，无须每本书重新生成一批人。管理员协调职责与创作人格分开，一个成员可以担任不同项目的负责人。

## 18. 数据迁移与回退

1. 用 SQLite 一致性备份方式创建快照，保留 schema 版本；不能仅复制正在 WAL 写入中的主文件。
2. 执行可重复的增量迁移，新增协作表，不删除旧表、不修改已有小说成果。
3. 创建默认工作空间。允许用户挑选或创建新成员，不将历史六个角色的全部记录自动归为新的个人记忆。
4. 对用户选择的旧小说建立通用项目映射，创建一个项目主群；成员由用户指定。
5. 旧记录通过唯一映射导入为历史时间线，保留原发言标签、原时间和来源。没有证据时不能伪造历史私聊、成员自主委派或验收记录。
6. 历史产物建立引用；后续新版本按新的提交/验收流程管理。当前正式版本需经校验确认。
7. 按项目切换执行所有权后才允许运行新任务。新项目默认协作模式，旧项目可以暂留旧模式。
8. 验证迁移前后项目数量、消息映射唯一性、产物 hash、章节状态和权限范围；相同迁移再次运行不得增加副本。

回退优先关闭协作入口、停止新调度，将新数据完整保留。只有已导出新交付并完成领域状态对齐的小说才能恢复旧执行所有者。通用项目没有旧系统对应执行方式，应保持只读可导出，不能承诺无损降级运行。

备份恢复是最后手段，需说明会覆盖快照之后的数据。稳定性观察期后再单独提出删除旧路径的清理变更。

## 19. 交付阶段与验收门槛

| 阶段 | 交付范围 | 验收门槛 |
| --- | --- | --- |
| P0 基线与契约 | 现有测试基线、迁移备份演练、领域/事件契约、交互评审 | 明确旧失败清单，新增表迁移可重入，确定首个闭环 |
| P1 成员与私聊 | 成员档案/版本、私聊、模型接入、工具循环、独立任务、最小交付 | 两位成员各自做文件任务，退出重进后身份、记录与任务保留 |
| P2 群组协作 | 自由建群、负责人模式、点名、成员 Session、委派受理、并行与回传 | A 分派给 B/C，两者独立执行；D 只在依赖满足后开始，结果回原群 |
| P3 任务与成果 | 任务面板、待办、版本、验收、成员负载、预算、恢复与隔离 | 可取消/重试/转交，双 worker 无重复最终提交，私聊/项目之间不串资料 |
| P4 小说融合 | 项目映射、领域适配器、岗位绑定、旧任务所有权、迁移入口 | 现有小说在群里完成真实首章规划、写作、审阅、验收和事实写回 |
| P5 默认体验与发布 | 首页切换、搜索、可访问性、移动端、桌面打包、运行观测 | 核心路径端到端通过、迁移/回退演练通过、新用户和旧用户均可完成任务 |

最先演示的闭环：创建两个不同人格成员 → 分别私聊并完成小任务 → 拉入群 → 负责人分派 → 成员独立产出 → 审阅 → 用户验收。这个闭环先证明核心体验，然后再引入长篇小说的复杂规则。

首版不包含：企业多人权限、成员市场、无限自动聊天、可视化任意工作流编辑器、全量外部连接器、未经验证的成员自动改写人格。定时主动任务可作为后续能力包，有明确授权和预算后添加。

### 19.1 工作量估算

以下为设计阶段估算，假设 2 名熟悉 TypeScript/当前仓库的全职工程师，设计与测试支持可持续参与；不包含模型费用与未知旧缺陷的大规模修复。

- P0：3–5 个工作日。
- P1：1.5–2.5 周。
- P2：2–3 周。
- P3：1.5–2.5 周，部分 UI 可与 P2 并行。
- P4：2–3 周，取决于旧流水线对成员配置的解耦程度。
- P5：1–2 周。

可用私聊/群聊试用版约 5–7 周；完成小说接入与发布验证约 10–14 周。P0 后根据测试基线和适配器试验重新估算。单人实施不能假设与双人相同的日历时间。

### 19.2 实施任务的拆分方式

每个阶段按纵向功能交付：数据库约束、领域服务、API、事件、UI、验收用例同步落地。先做只读查询和幂等命令，再开启后台执行；避免只做好整个数据库和整个 UI 后才首次联调。

建议首批提交依次为：新增 schema 与契约；成员创建/查询闭环；私聊消息/SSE 闭环；单成员工具任务闭环；群创建与成员会话；委派与回传；任务验收。每批可独立构建、测试与回退，不一次重写整套系统。

## 20. 测试与发布标准

### 20.1 必须自动化验证的场景

| 范畴 | 验收场景 |
| --- | --- |
| 身份 | 改名、换模型、换项目后 ID 稳定；人格版本不影响正在执行的旧运行 |
| 真正执行 | 模型调用实际工具，产生可检验文件，工具失败后任务不能宣称已完成 |
| 群调度 | 普通消息仅负责人响应；有效点名路由正确；引用里的 @ 不触发任务 |
| 委派 | 请求/受理/失败/回传可追溯；重复回传不重复开启后续任务 |
| 并发 | B/C 可并行；同 Session 串行；同产物的冲突写入不会互相覆盖 |
| 任务依赖 | 依赖未通过不启动；拒绝/取消可传播；循环依赖被拒绝 |
| 用户控制 | 执行中补充要求、暂停、取消、离群和权限撤销均能正确处理 |
| 恢复 | Worker 在工具返回前后崩溃、租约过期、重复消息、SSE 重连均不丢任务 |
| 记忆隔离 | 私聊内容不自动进入群；小说 A 事实不进入 B；删除后检索不再命中 |
| 执行安全 | 拒绝路径穿越/越界符号链接、越权工具及伪造发送者；资料中的恶意指令不能扩大权限，日志不泄露密钥 |
| 成果验收 | 审稿绑定版本；输入变更使旧验收失效；未验证文件不能完成任务 |
| 小说兼容 | Canon、质量门禁、章节恢复、事实写回保留；新旧 worker 不能同时推进同一项目 |
| 迁移 | 反复执行不重复导入；消息/文件可追溯；备份可恢复 |
| 前端 | 长消息、空状态、失败重试、离线、窄屏、键盘焦点、草稿恢复 |

结构与调度用可控假模型和工具替身验证；实际模型另做固定场景评测，分别评估口吻一致、独立意见、工具完成率、交接准确度和不必要发言比例，不能仅凭“看起来像不同人”验收。

Playwright 覆盖桌面 1440px、1024px、手机 390px 与 360px，检查重连后时间线、任务动作、详情抽屉和输入框。新增能力测试必须通过；受影响的旧链路通过回归，历史无关失败单列原因，不用它们掩盖新增回归。

建议运行指标：接单成功率、任务验收率、重复交付数、恢复成功率、平均排队时间、用户介入次数、每项验收成果的 token 消耗。发布前以固定夹具建立实测基准，指标数值不在设计阶段虚构。

## 21. 首版完成的定义

用户能创建并持续使用多位有不同人格和专长的成员；能私聊完成独立工作；能自由组群并指定目标；成员能真实分工、执行、协调、交付和接受审阅；用户能看到依据、状态和结果并介入；项目归档后成员仍可参加新项目。

小说场景同时要求：至少一个迁移的旧项目和一个新建项目能通过群组完成一个真实章节的完整闭环，且保留已有正式事实与质量约束。

## 22. 评审时可调整的决策

实施按本文默认值可以启动，以下决定可在对应阶段评审时调整，不阻塞方案本身：首批成员模板、人格字段文案、默认协作模式、初始能力包、任务预算与并发默认值、旧项目自动迁移的覆盖范围。影响身份隔离、任务状态机和数据一致性的修改须在契约层评审后落地。

本次交付还包含会话内交互预览，展示群聊、成员私聊、任务详情和验收操作。预览使用示例数据和本地状态，仅用于评审界面；不连接模型，不代表上述服务已实现。

预览已通过浏览器交互检查：发送、草稿保留、建群、负责人必须属于群成员、定向消息、成果验收、退回修改和移动端导航。已检查 1024px、736px、390px、360px、320px 布局及深浅主题，无浏览器脚本错误。这些结果仅针对预览，不替代实施阶段的真实 API、模型、worker 和迁移测试。
