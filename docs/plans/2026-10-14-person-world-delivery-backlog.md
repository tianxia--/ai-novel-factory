## 1. 第一阶段要交付什么

产品主线已按用户确认调整为 IM：创建群、邀请已有独立人物、讨论目标、分别调用各自能力。任务/审阅等工程机制按需出现，不是聊天之前必须完成的流程。第一阶段场景：

> 我创建小说群，邀请编剧、作者、编辑，提出要求；大家先讨论怎么写，再分别开展获准工作。作者可私聊编剧求助，编辑可独立审阅共享版本；成果回到群里。我可以观察各人的世界，但不代发、不改变其处理状态。先用普通工具证明能力独立挂载，后接真实小说工具。

小说正式写回在领域适配阶段加入。此前可用受控文本成果验证同一机制，不宣称已完成小说生产闭环。

## 3. 固定测试场景

测试工作空间 W1 中有人类 U、协调人 L（林岚）、作者 C（陈墨）、编辑 Z（周宁）。另一工作空间 W2 有隔离成员 X。

- 群 G：U、L、C、Z 已接受邀请；新成员 N 处于邀请中。
- 私聊 D：C 与 L；U 不是参与者，但在独立的只读观察授权下可观察自己管理的 C 或 L。
- 资料 A：仅 C 可用，含随机 canary 字符串，不含真实秘密。
- 资料 B：对 G 授权，包含章纲；成果 V1/V2 不可变，审阅明确引用版本。
- 任务 T：U 请求、C 接受、Z 审阅，等待问题 Q 的答案。
- 底座执行全部使用试验目录与短期凭据，不借用真实个人浏览器登录态。

Harness 试验先用可审计工具 stub，记录所有副作用；再用隔离环境中的真实文件和受控 HTTP 接收器。不能用真实购买、外部邮件群发等动作来验证重试。

## 5. Harness 试验的 Go / No-Go

### 5.1 必须通过

- 不同成员的 Session、工具权限、文件资源和凭据可隔离。
- 可可靠识别输入是否已接收、执行是否已收束；不确定时有显式停机核对路径。
- 可停止某位成员而不强制终止其他人的正常工作。
- 无副作用地读取已提交的 Session；观察不需要重新唤醒模型。
- 可以拦截业务写工具，执行身份绑定、幂等/效果核对与具体动作审批。
- 崩溃后恢复不会重复公开消息或已确认的工具效果。

硬门槛失败时不能靠综合评分平均掉。可用独立进程/沙箱解决的问题，要把新增运行和运维成本记入决策；若仍不能满足，换候选或缩小首版能力。

### 5.2 同条件比较，不预设性能结论

记录首次响应、等待恢复、停止收束耗时的分布，峰值内存/进程数量、三人并发下排队、持久化体积、模型用量、恢复人工步骤。固定模型版本、输入、工具和并发度，并写明样本量与机器配置。

PoC 建议五个工作日时间盒；这不是保证五天完成上线。若模型访问、版本或隔离环境尚未就绪，输出阻塞清单和已验证范围，不自动延期伪称进展。当前不承诺完整项目工期，P01/P06 后重新估算。

### 5.3 报告模板

```text
候选与精确版本：
SDK / API 规范版本：
模型、工具、隔离配置：
执行日期与机器：
测试 ID / 输入 / 预期 / 实际 / 原始记录路径：
通过、失败、未测：
适配器补齐项与运维成本：
明确不支持的能力：
决定：通过 / 限定范围通过 / 不通过
```

## 6. 故障注入点

对消息、等待和工具执行至少覆盖以下窗口：业务事务前；业务事务后但 outbox 未发；Harness 收到但适配器未收到 ACK；工具生效但回执未入库；等待登记后但当前 Run 未结束；停止请求后底座仍在执行；授权撤销后但旧 SSE/读取响应还在路上。

每次恢复都同时检查“有没有丢工作”和“有没有重复动作”。只检查进程启动成功不算恢复测试。未知外部效果不允许为了测试变绿而自动当成功或失败。

## 7. 每批次完成定义

1. 运行代码修改前完成 GitNexus 影响分析，明确直接调用者和受影响流程；HIGH/CRITICAL 先报告。
2. 增量测试覆盖新增行为和最危险的失败路径；记录旧测试基线，不隐藏既有失败。
3. 业务写入不绕过授权、事务、版本与效果账本；新路由包含直接越权测试。
4. UI 有加载、空、失败、只读和权限撤销状态；无假进度或伪造已完成。
5. 迁移可重复执行，有兼容读取/回退说明，不破坏原小说项目。
6. 如用户要求提交，先 `gitnexus_detect_changes` 核对范围；提交后按仓库约定刷新索引并保留已有 embeddings。

## 8. 产品确认建议

推荐先确认三个默认值：所有者可以只读观察自己创建的 AI；群默认只开放加入后的历史；内部私聊可以在预算和联系权限内自主发生。三者决定了数据模型和信息边界，比先选人物头像或卡片风格更重要。

在这些默认值未被修改前，可以继续细化界面与测试场景；开始真实实施时再冻结版本、权限策略和第一批人物配置。外部真实用户加入、私有数据跨组织共享和人工接管均不自动纳入本期。

## 9. 交付关口与首版范围

P00–P10 是工程批次，不是十一次用户发布。建议收敛为三个交付关口，先完成可运行的真实闭环，再扩大使用范围。

| 关口 | 覆盖批次 | 用户能实际完成 | 不得省略的门槛 |
| --- | --- | --- | --- |
| R0 技术准入 | P00、P01；P02/P03 的契约可同步准备 | 尚不提供生产入口 | 固定 Harness/模型/隔离环境的真实停止、恢复、观察试验；未通过不能宣称可用 |
| R1 私有试用 | P02–P07，加 P08 中资料权限/撤权/备份的必需部分 | Provider 配置、人物模型与能力挂载、建群讨论、私聊协作、观察各人；按需交付通用成果 | 真实 Harness 运行与服务端授权；不依赖小说工具；无关键越权/重复效果 |
| R2 小说试点 | P08 完整能力、P09、P10 | 新小说和迁移小说的首章闭环，来源明确的经历与经验 | 版本门禁、Canon、迁移互斥、恢复演练、代表性人物回归与人工验收 |

R1 的人物档案、经历和记忆入口可以从简单列表开始，但数据必须真实且有出处；不能用假记忆占位。自动经验候选可延后，明确的业务约定与资料权限不能延后。

人物创建默认 paused，启用单独检查。新建人物不调用付费模型生成履历；人物模板提供的是配置。详见[详细设计第 16–18 节](2026-10-14-person-world-detailed-design.md)。

## 10. 人格质量与流程质量分开验收

确定性测试覆盖身份、权限、承诺和版本，不要求模型逐字重复。风格与专业表现使用固定场景、相同授权资料和可追溯输出，由人工抽查；记录模型/人格/技能版本以及失败样例。

建议首批至少包含：普通寒暄、明确交办、信息不足、同事分歧、跨群资源冲突、私人资料请求、错误事实更正、压缩后续接、换模型后的工作延续。这是待执行的场景集合，不是已验证结论。

验收不使用一个总分掩盖硬失败。能完成任务但泄露私聊不通过；风格很像人但承诺丢失不通过；安全符合但专业成果不合格则继续调整能力配置和任务范围，不能标为已验证专长。
